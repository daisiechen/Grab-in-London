# Fancy 中文产品需求文档

版本：v0.8 · R1 开发交付规格；更新：2026-10-19。状态：业务方案已确认，Web Demo 为内存模拟；真实服务与 iOS 尚待研发及验收。本文替代旧版同名 PRD 的当前规则；Git 历史保留旧版。需求真源为本文，技术与数据细节见 [R1 研发契约](../../shared/README.md)。[开发准备评审](../reviews/development-readiness-2026-10-19.zh-CN.md)记录 R01–R22 的跨端复核，不以本文件的存在代表评审通过。

## 1. 需求背景、定位与验证目标

在伦敦缺少社交圈、时间有限的人，希望有人一起吃饭、聊聊天。餐厅往往需要提前预约，与陌生人见面又涉及背景、氛围、人数、费用和可靠性的不确定性。这来自用户提出的产品问题，尚不是经过真实样本验证的市场规模或付费意愿结论。

产品把一顿本来就要吃的饭，变成认识新朋友的机会。主要动机是陪伴和建立日常连接；networking、文化交流是可能的附加价值，不以职业地位、招聘或 dating 匹配作为首期主线。用户自主选择饭局并了解参与者背景，发起人审核申请。首期验证“从发现合适饭局到真实见面，再到愿意回来”的完整链路。

品牌暂定 **Fancy**；英文 slogan **Meet new people over a meal.**；中文 slogan **吃个饭，认识一下。**。邀请语 **Fancy a bite? / 一起吃点？**；欢迎辅助句 **There’s a seat for you here.**。商标、域名和平台账户检查是上线依赖；旧仓库及演示 URL 不代表最终品牌注册。

### 1.1 产品目标与设计原则

1. 让第一次加入足够轻松：发现优先，底部突出 Create meal；个人背景、费用与餐厅状态先于申请展示。
2. 明确承诺：申请不占席位；批准即确认席位；外部预约声明不等于供应商确认。
3. 主动选择与边界：没有陌生人任意私信；群聊与席位授权关联；餐后私聊要求双方有效出席与互选。
4. 信任来自上下文和共同经历：个人介绍不变成履历排名；体验评价为私密整场反馈，不公开个人星级。
5. 可恢复：返回保留草稿，失败保留输入；同一请求重试不重复产生席位、消息或通知。
6. 复用现有 forest / ivory / citrus、餐桌视觉、精灵助手和地图；不因收敛 R1 重做品牌或移动端运行时。

### 1.2 成功指标与证据边界

| 问题 | 观察方式 | 限制 |
| --- | --- | --- |
| 能否找到合适饭局 | discovery_results、detail_view、申请轮次与首次确认 | 真实埋点 SDK 未接入；Demo 的业务投影不是流量证据 |
| 发起是否顺畅 | create_started → create_arranged → meal_published，同一 attemptId | 不能把不同会话的事件拼成完成 |
| 能否见面 | 有效开始时成员及出席结果，按来源区分 | unknown 不等于 absent；没有人工核实出席 |
| 是否愿意回来 | 私密整场评分、愿再参加、之后再次参加 | 无评分/无回答不能填默认正向值 |
| 是否形成连接 | 满足资格的双方互选与后续使用 | 不向统计导出单方互选；连接不代表真实友谊 |

申请→出席的阶段观察点为 **startsAt+24h**，不是 scheduledEndAt+24h，也不是七天后的最终封窗。餐后可编辑窗口以 scheduledEndAt+7 天结束。样本、分母、asOf、未知数分别展示，不编造目标增长幅度。后台口径见 [测量契约](admin/measurement-contract.zh-CN.md)。

## 2. 版本范围与实现状态

R1 采用 **D1：各自到店支付 + 发起人外部订位**。本次默认 Demo 入口为 R1；`?scope=future` 独立保留后续预付/应用内预约探索，不能据此承诺 R1 提供真实交易。

| 能力 | R1 产品要求 | 当前 Demo | 后续/真实接入依赖 |
| --- | --- | --- | --- |
| 平台 | iOS App + mobile Web；后台 desktop Web | 带 iPhone/Pixel 外壳的 Web；不是原生 iOS | 原生实现、签名、平台账户、上架与设备验收 |
| 登录 | 邮箱验证码、Apple、Google、Facebook | 授权与验证码预览，本地身份；无真实 provider/邮件 | 四渠道配置、服务端验证、会话与账号关联 |
| 发现/申请/管理 | 2–6 人，自主选择，发起人批准 | 内存规则与页面可操作 | 服务端存储、并发与定时任务 |
| 餐厅/费用 | 手工餐厅信息、必填预算、自行到店支付 | 本地候选地图与手工填写 | 无库存接口前不得显示真实余位 |
| 预约 | 发起人外订声明，T−15 检查 | 声明与时间推进模拟 | 服务端任务；不调用餐厅 |
| 群聊/餐后/私聊 | 依权限、出席和双方互选开放 | 本地多角色验收 | 持久消息、推送及滥用防护 |
| 助手 | 确定性找饭局、生成草稿，偏好显式确认 | 复用现有精灵；不自动申请/发消息 | 真实 LLM、语音、跨设备偏好在后续 |
| 支付/平台代订/退款 | 不进入 R1 | 独立 future 场景保留 | 支付、供应商、退款与相应合规设计 |
| 公开个人 references | 推迟 | 不在 R1 发布个人评价 | 后续独立决策 |

商业假设：先验证吃饭社交价值与供给；餐厅合作、按次付费或会员须通过真实实验决定。不以付费身份凌驾普通成员，不把“未来可变现”当已验证收入模式。

## 3. 用户与路径

| 用户/角色 | 触发与需要 | 路径及完成结果 |
| --- | --- | --- |
| 新到伦敦/社交圈小的首次加入者 | 找到时间地点合适、知道和谁吃的饭 | 欢迎→访客发现→详情→登录/介绍→申请→待审→批准→群聊→到店→餐后自报与反馈 |
| 忙碌的本地回访者 | 快速安排一顿饭，可再次遇到熟人 | 发现/Meals→查看背景与曾同桌关系→申请；不把曾同桌自动当优先席位或自动入群 |
| 发起人 | 找到合适伙伴并落实餐厅 | Create→餐厅→时间人数→预算介绍→预览发布→审核主页与申请→批准→外订声明→群聊协调→餐后补缺失自报 |
| 已确认后退出者 | 改变安排且知道影响 | 详情→退出确认→释放席位→保留已授权群聊只读；截止前可新一轮申请，再等批准 |
| 饭后希望再联系者 | 有边界地建立联系 | 餐后自报→整场反馈→选择具体同桌→双方有效出席并互选→私聊；可随时撤回或拉黑 |
| 创始人管理员 | 低人力处理必要举报与数据检查 | 同一登录体系 + 服务端 allowlist→后台；没有人员账号管理、人工出席核实或完整客服系统 |

访客可浏览饭局公开摘要，不能读取完整成员背景、申请、群聊、单方互选或举报。正式服务必须在服务端投影字段，不能仅靠隐藏按钮授权。

## 5. 时间、状态与容量规则

所有权威时刻存 UTC，显示及输入解释为 Europe/London；界面给出 BST/GMT。DST 不存在的墙钟时间不能提交；重复小时要求显式选 offset，不能由设备所在时区猜测。scheduledEndAt 默认 startsAt+2 小时。

| 截止 | 条件 | 后果 |
| --- | --- | --- |
| 发布 T−60 分钟 | 距开始至少 60 分钟，等号允许 | 之后不可发布该开始时间 |
| 申请 T−45 分钟 | 当前时刻严格早于此点 | 到点停止新申请与重申 |
| 审核 T−30 分钟 | 严格早于此点，待审且有席位 | 到点未决申请 EXPIRED；此后不能批准 |
| 外订 T−15 分钟 | 严格早于此点声明；到点检查 | 人数不足或未声明/声明人数不等于检查时确认人数，整场自动取消 |

2–6 人含发起人。双人 minimum=2；3–6 人 minimum=3。容量与生命周期分别存储：OPEN 可呈现申请开放/申请关闭/审核关闭/已满/进行中；COMPLETED 按计划结束；CANCELLED 保留取消原因与时间。满员不等于结束，外订声明不等于确认席位。

定时检查按其计划时刻计算历史人数，幂等执行；服务端命令执行前统一补齐到期事件，延迟任务不得造成过期批准、已取消饭局仍发消息。前端刷新可促使查询，不是任务权威。没有补位、候补名单或截止后的重新开放。

T−15 检查通过后有人退出而低于原最低人数：**由发起人决定继续或取消**。保留原 minimum、当前人数、决定及时间；继续后不再次自动取消、不补位，发起人自行联系餐厅。再次减员可在开饭前重新要求决定：清空当前决定时间/人数，保留每次 pending/continue 的人数、时间与序列历史。若开饭时仍未决定，记录 unresolved-at-start 并一次通知；不自动取消、不推定发起人同意，原最低人数保留。开饭后该事实只读，不再显示无法执行的继续/取消待办。T−45~T−30 可审核已有申请但不能新申；T−30~T−15 按退出后的实际人数及声明匹配检查。

## 6. 功能规格

### FR-01 身份、注册与资料

入口：欢迎主按钮、申请/创建/个人功能的登录门槛。访客可退出到发现。登录后返回原饭局/原动作，不自动提交申请。

- 邮箱输入 trim、格式校验；验证码六位，服务端单次使用、过期、重发冷却、速率限制及尝试次数控制。失败保持邮箱与原意图；重发使旧码失效。Demo 使用样例验证码，不投递邮件。
- Apple / Google / Facebook 预览包含继续、取消、失败、关联冲突。真实登录用 provider subject 稳定关联；同邮箱不自动合并账号。关联冲突回已有账号重新认证后处理；取消回原登录页，不产生空账号。
- Facebook 缺失邮箱、Apple relay 投递失败：仍提供站内通知，在设置补充并验证通知邮箱；不得宣称邮件必达。该补邮箱入口为真实接入的研发验收要求，当前 Demo 未验证投递。
- 新用户须自我声明 18+、确认社区与隐私信息；不采集证件或生日核验。照片/简介为用户自主介绍，不推断敏感属性。
- 名字 2–40 字符，介绍 20–1000，至少一种语言和一个兴趣。首期工作/学校/来自哪里是可选上下文，不做等级排序。保存前与服务端再次验证；资料不完整时申请与发布给出修复路径。
- 当前 Demo 身份为本地预设账号；不构成真正账号合并、服务端鉴权、持久会话或重新认证实现。

### FR-02 Discover 与筛选

默认地图与列表可切换。日期快筛仅打开日期；人数快筛级别高于预算；全部筛选包含日期、人数、预算、语言。弹层使用样式一致的选择控件，草稿选择→Show tables 才生效；退出不改已应用条件；清空后可恢复结果。列表中的标题、餐厅、区域、London 时间、预算、确认人数一致。

地图为既有本地素材与可拖动/缩放视口；数字表示事件数，不是可容纳人数。当前 R1 按已知区域聚合标记，数字为该区域匹配事件数；点击标记筛出该区域全部匹配饭局，并高亮所选区域，不更改创建草稿。Search this area 显式应用当前视口范围，Show all areas 恢复。区域坐标沿用现有地图配置，不按列表序号随机定位；手工餐厅的未知区域不伪造坐标，提示并保留在备用完整列表中。列表显示所选范围完整事件；整卡点击详情，头像独立打开主页，不重复 View meal。

查询仅返回当前匹配数据，取消/过期饭局不作为可申请推荐。空态说明无匹配，提供清空和发起入口。真实列表使用稳定排序与 cursor、asOf；加载/失败保留已应用条件和原列表，不能把错误当“没有饭局”。

### FR-03 详情与申请

详情区分餐厅名、地址、区域，地图按钮带定位图标与明确外链文字；虚构候选只跳真实区域，不能声称该地址存在。展示预算、支付规则、人数/最低人数、语言、发起人/当前成员、申请/审核/预约截止及外订状态。

申请输入 20–300 字；服务器校验身份、资料、未取消未开始、申请时间、容量及当前轮次。提交成功写新的 applicationId、PENDING，详情/Meals/Inbox 同步；不计确认人数、不开放群聊。重复同一 intentKey 返回同结果。

| 当前轮次 | 行为 | 结果 |
| --- | --- | --- |
| 无/已撤回/已退出确认 | 截止前申请 | 新 applicationId；原记录不复用 |
| PENDING | 本人撤回 | WITHDRAWN，可截止前重申 |
| PENDING | 本饭局发起人批准 | CONFIRMED，原子占席、开启授权区间与群聊；不需再次群主确认 |
| PENDING | 发起人拒绝 | DECLINED，本饭局不能重申 |
| PENDING | 审核截止 | EXPIRED，通知申请者 |
| CONFIRMED | 本人开始前退出 | CANCELLED，记录 withdrawnAt；释放席位并冻结该区间消息 |
| 非待审/无权对象 | 批准/拒绝/撤回 | 拒绝，不更新其他饭局或他人记录 |

并发最后一席采用版本检查/事务，只有一个成功；冲突刷新后展示真实人数，不能按按钮点击先乐观确认。API key、applicationId、mealId、userId 分别建模；不能 find 第一条历史申请代替当前轮次。

### FR-04 Meals、退出与整场取消

Meals 分 Upcoming / Past / Cancelled；个人退出状态与整场取消不混为一个字段。申请/确认饭局均可进入详情查看状态。本人确认退出须二次说明：席位释放、历史只读、重新申请须发起人重新批准。never-confirmed 不获得任何群历史。

发起人不能普通退出、移除确认成员或转移主持，只能开始前取消整个饭局。取消原因命令仅接受 host / host_changed / other 固定代码，不能将自由文本用作 reason；私密说明不进入通知或统计。取消收件人限定发起人、当前确认成员及当前待审申请者，不给已拒绝/撤回/退出/过期人群广播，群聊停止发送，预约由发起人外部联系取消。R1 没有平台退款或罚款；迟取消与缺席只作内部记录，没有公开惩罚/自动处罚。

### FR-05 Create meal

四步：餐厅→时间人数→费用与介绍→预览。每步 Continue 校验本步必填，返回和 Save draft & close 保留内存草稿；刷新丢失是当前 Demo 限制，真实客户端应按账号持久草稿并提供删除草稿。

1. 餐厅：既有地图候选先浏览再 Use this restaurant，或手填名称 1–100、地址 1–200、区域 1–80；地图 URL 可选 HTTPS 白名单链接。不依赖 Places、库存或定位权限，不伪造有位。
2. 时间人数：日期、London 时间、DST offset；2–6 人含本人，默认突出小桌；开始至少一小时后，end 默认两小时后。
3. 费用与介绍：预算上下界必填，正数、上界≥下界，GBP 精确到便士；语言代码数组至少一项；标题 5–80，说明 20–1000。到店各付自己的订单是固定 R1 支付协议，不能选择平台预付。
4. 预览：展示全部安排与外订责任，Publish 后只创建一次新 mealId、host 成为确认成员，跳详情。未订餐厅仍允许发布；不自动虚构外订声明。

失败保留草稿；重复点击和结果未知用同一个 intentKey 查询/重试；提交后才消费草稿。未来支付流程仅独立 future 场景。

### FR-06 发起人管理与外订

从详情 Manage your table 进入；本人饭局以外拒绝访问。待审卡先看个人主页和申请介绍，再 Approve seat / Decline。确认列表来自席位记录。

未有任何客人确认时可更改关键安排并重新校验；变动使旧外订声明失效。**一旦有客人确认**（包括后来已退出），时间、餐厅、费用等关键安排锁定；标题/描述仍可修改。要改关键安排须取消原饭局、新建新 mealId，replacementFor 只链接原已取消且自己发起的饭局，不搬运申请或同意。

外订声明弹层显示餐厅、开始时间、当前确认人数，发起人明确确认“已在应用外预订”。保存 declaration(at,count)，通知当前成员。人数变动必须在 T−15 前重新声明；不能在检查后追认。声明是发起人自报，不是餐厅供应商确认。检查失败整场取消并列出人数不足/未订位或人数不符的所有原因。

### FR-07 Inbox、群聊与通知

Inbox 同时列待审入口、确认群聊、可读历史、有效私聊与站内通知。待审项显示状态并打开详情，不显示聊天输入或群消息。批准席位即自动授权群聊，无第二次发起人确认。

消息绑定 conversation/meal/member，长度 1–2000；clientMessageId/intentKey 去重；按发送服务端序号分页，不用手机时间决定权限。确认成员可读各次授权区间的并集，不能读取退出与重新批准之间消息；退出/整场取消/结束后保持已授权历史只读。blocked 读者隐藏被拉黑成员正文；不把拉黑当退出同一饭局。

无编辑/撤回消息功能。发送前重新检查当前对象、成员关系与生命周期；失败/离线保留输入，拒绝后更新权限；不使用其他饭局的 draft 或 read cursor。

| 业务事件 | 收件人 | 站内/邮件与深链 |
| --- | --- | --- |
| 新申请 | 发起人 | Host 对应 applicationId |
| 批准/拒绝/过期 | 申请人 | 详情状态；批准含群聊入口 |
| 退出/人数变动 | 发起人；需行动时当前成员 | 管理/外订声明 |
| 外订声明/取消/最低人数决定 | 受影响成员 | 详情；取消后只读 |
| 群消息/双方连接 | 有权限成员/双方 | 对象内消息；不泄漏单方选择 |
| 举报提交/处置回执 | 举报人 | 自己的 case，不向被举报人泄漏提交者 |
| 安全/删除/导出 | 本人 | 设置及请求状态 |

通知 id 按事件×收件人×channel 去重；站内是可回看事实，邮件投递状态独立 pending/sent/failed/retry，iOS push 补充。可关闭推荐等非必要通知；必要业务/安全仍站内保留。失效深链返回不可用说明及发现入口，不能跳错饭局。Demo 只模拟站内，不宣称邮件/push 已投递。

### FR-08 出席与整场体验

计划结束后开放，至 scheduledEndAt+7 天（等号关闭）；只有开始时有效成员，未取消整场、确认早于开始且未在开始时或之前退出。历史多轮按开始时那一轮判断，不以“曾确认”就算有效。

本人最新自报优先，发起人仅补本人缺失项；保留每次来源、时间、server sequence 及先前差异。没有后台人工核实出席，不等待裁决，不用 verified override。unknown 作为未知，不当缺席。同时间以服务端序列排序。

有效 present 才可保存私密整场评分（1–5，**无默认值**）、是否愿再参加（必答、无默认值）、可选原因 company / conversation / coordination / expectations / venue / cost / other。原因可以为空，不能预选负面/正面原因。保存按 mealId+userId upsert 并保留版本；回访加载本对象已保存值，切换对象不沿用另一桌草稿。

反馈不是公开个人评价。本人将出席改为 absent 后，已有反馈保留必要修订事实但退出有效统计，互选私聊发送权限同步失效。超过窗口不可新建/修改上述报告，不影响隐私撤回或拉黑。

### FR-09 互选与私聊

同一共享饭局中，双方均具有效 present，且双方有效互选、无任一方向拉黑，才开放私聊；单方选择不通知另一方。互选创建/编辑限制七天窗口，撤回任意时间允许。撤回针对“这个人”：清除本人→该人在全部共同饭局中的有效同意，不能因另一场仍有旧同意而继续发送。对方自己的选择保留但不自动恢复联系；本人重新选择仍须满足对应饭局七天窗口、有效出席等条件。撤回或任一拉黑立即禁发，历史保留只读；解除拉黑不恢复旧同意，须重新选择且仍满足创建窗口。

禁止跨饭局拼接 A 在饭局甲选择 B 与 B 在饭局乙选择 A。出席修订使资格失效时重算，不通过缓存继续发送。连接状态与各人 choice 分离；前端不得用 UI 隐藏替代服务端判定。

### FR-10 个人主页、安全与举报

主页展示经允许的名称、照片、介绍、兴趣、语言与可选背景。邮箱、单方互选、举报正文、后台备注不公开；拉黑任一方时隐藏可识别背景；所有入口（头像、列表、搜索、深链）应用同一投影。公开个人 references 推迟。

用户可在成员主页提交私密举报：对象、固定分类和 5–1000 字说明；提交后自动回执 caseId，提供立即拉黑。case 至少 received / in_progress（处理中）/ resolved，处置须有依据与审计；举报人只看自己记录。不能以少人力取消必要安全响应，也不承诺不存在的 SLA/全天人工客服。

R1 上线前需最小 UGC 检测（发布/资料/消息输入检查、命中拒绝与解释、申诉/举报路径），创始人服务端 allowlist 处理必要风险，提供真实可联系支持入口；配置未完成阻断上架，不能用假地址占位。依据 [Apple App Review Guidelines §1.2](https://developer.apple.com/app-store/review/guidelines/)。该条为 iOS 研发前置规格，不代表当前 Demo 已集成内容安全服务。

### FR-11 设置、数据与账号生命周期

设置集中通知偏好、分析同意、导出、社区/支持、注销、删除。注销只撤销会话不删除账号；重放/重置只留验收模式。资料、反馈与通知按用户隔离。

删除路径：再次认证→明确不可逆影响→输入 DELETE/二次确认→原子创建删除任务。应用自动取消本人尚未开始的主持饭局、撤回申请/退出未开始参与；已开始饭局保留生命周期与他人餐后资格，主持身份去标识，已开始参与只保留去标识历史关系、不新建低人数待办，通知受影响者，撤销全部会话/互选，清理资料、自己消息正文、申请介绍等个人内容，对必要历史去标识，不要求用户无限手动清空饭局。保留法定记录必须列明依据及最小字段，不能用“业务审计12个月”保留个人聊天正文。删除任务失败可重试并显示状态；处理未完不声称完成。规范依据 [Apple 账号删除要求](https://developer.apple.com/help/app-review/guideline-reference/5-1-1-account-deletion)。Demo 在本地快照模拟清理，不是真实重新认证/后台异步删除。

导出：仅本人资料及本人申请、出席、反馈、单方选择、本人消息、举报，不导出他人私密数据。生产导出需重新鉴权、有期下载、审计。删除覆盖应用控制的活动库、索引与缓存，备份采用到期清理/恢复后重放删除日志；不能声称远程删除别人已下载的副本。

可选行为采集先同意，可撤回，撤回停止后续可选采集；业务履约必需记录独立说明。原始行为暂定90天、最小业务/审计暂定12个月，期满清理、账号删除去标识；最终合法性及例外经专项审查，不能声称已合规。真实通知邮箱/隐私文本/联系方式为上线配置依赖。

### FR-12 精灵助手

沿用按需浮动入口、拖拽吸边与收起，非底部导航、不主动打扰。只消费当前可公开且符合筛选/截止条件的饭局，取消/新建后重算；未知 mealId 友好恢复，不能 non-null 崩溃。打开主页可继续30分钟未过期会话，偏好仅明确确认才保存，可纠正/删除。

找饭推荐→查看详情；申请/消息/创建草稿→填回既有编辑器，由人审核提交，所有权限和截止规则复用。不能自动占座、批准、发消息或改预约。真实模型/语音/跨设备在后续；保留现有素材，不在 R1 声称 live AI。

### FR-13 数据投影与研发对接

权威业务 JSON 使用 `contractVersion: r1-1, demo: true, asOf, users, meals, applications, attendance, feedback, events: []`；详细字段、API/error/idempotency/CRUD说明见 [共享契约](../../shared/README.md)。该文件是手工模拟 handoff，不是真实前后端连接。

导出排除姓名、bio、聊天/举报/申请正文、单方互选及任意自由文本取消理由；title 用稳定匿名占位，保留分析必要 ID/时间/区域/预算/人数/出处。fixture 普通人作为虚构数据集内部 regular 默认，不因 demo 环境而全标 test；operator 不导出。后台仍显式标记该数据集为 demo，不混入生产。

R1-1 不携带交互事件（events=[]）；实际 SDK 的 consent、匿名映射、去重、迟到及90天清理必须另验收，不能把业务投影当真实发现漏斗。未知字段拒收，不能悄悄吞私密内容；无效文件不覆盖现有快照。

## 8. 输入、兼容与边界验收

语言存 BCP47 受支持代码数组（首期 en/zh/fr/es/de/it/ja/ko/ar/pt/hi）；展示名称本地化，不用分隔字符串作权威。货币为 GBP 整数便士；预算新记录必填，历史缺值显式 unknown 不默认0。使用 ISO UTC，拒绝无效日期、非法整数、NaN、倒序时间与长字段。客户端校验辅助、服务端再次校验。

| 场景 | 必须可观察结果 |
| --- | --- |
| T−60 发布及各截止等号 | 发布等号可，其余对应命令截止等号不可 |
| 同意图重试/参数换用/并发最后位 | 重试同结果；换参数409；只有一个确认成功 |
| 多轮撤回/退出重申 | 新 ID；群历史区间并集，无间隙消息 |
| 任务延迟、人数变化、预约人数不符 | 以计划检查点历史事实取消；通过后减少由host决定 |
| 出席变化/七天窗口 | 本人优先、未知保留；统计与私聊实时重算；隐私撤回不受窗口阻止 |
| 离线/503/401/403/409/404 | 保留可恢复输入；重试同意图；按最新权限显示，不错误宣称成功 |
| 不同meal/user/application切换 | 草稿、反馈、消息和通知不串对象 |
| 删除与导出 | 原子撤销联系与会话、去个人内容；导出白名单、不可泄漏他人私密字段 |
| 长文/无图/无数据/取消深链 | 换行、替代头像/区域，明确空态或不可用恢复 |

平台验收：iOS 与 mobile Web、后台 desktop Web 分开。当前 Web 验证 iPhone/Pixel 运行壳、触摸目标、键盘避让、独立滚动、底部创建入口；不代表原生、离线同步、读屏完整合规或真实网络已通过。链接/表单使用语义名称与可见焦点，卡片与头像独立按钮，键盘 Enter/Space 可达，错误 role=alert、成功 role=status；减少动态效果、对比度与读屏需专项设备检查。
