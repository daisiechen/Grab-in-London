### 0.2 创建、截止、成团和预约

- 创建保留Arrange / Introduce / Costs / Review四步；人数输入最低人数和上限，人数均含发起人。发布后首位成员获准即锁定最低人数、容量及关键安排。
- 发起人设置统一招募截止closesAt，默认startsAt−60分钟，可提前，最迟startsAt−30分钟；发布时必须晚于当前时间。到达截止时刻（now ≥ closesAt）停止新申请和审批，待审申请变EXPIRED。
- 截止检查confirmedCount ≥ minimum；未达最低自动取消。达标后至开饭前再跌破最低，立即取消。发起人不能临时降低minimum绕过检查。后台任务迟到仍按计划检查时点与成员历史重建，不因执行延迟跳过终局。
- 开饭时冻结出席资格名单：发起人及当时已确认、未退出成员；退出恰好发生在开始时刻者不在名单内。开饭后不再因人数变化自动取消，不允许修改过去的成团或出席事实。
- 审批与退出必须原子校验名额。首期无付款保留；pending不占位，批准直接CONFIRMED并入群。交易参考路径中的30分钟保留不用于首期。
- 外部预约声明记录餐厅、时间、人数和更新时间，明确是发起人报告而非平台验证。确认人数变化后旧声明标为需更新；发起人联系餐厅调整并重新声明。预约取消/失败不等同整场取消，也不关闭群聊。
- 无人获准前，发起人可修改关键安排并重新验证截止及预约声明；有人获准后，餐厅、日期、时间、费用、人数范围、截止锁定。需要改动则取消原场、创建新场，原成员必须主动重新申请，不自动搬迁。

### 0.3 申请、退出与整场取消

| 当前状态 | 允许动作与结果 |
| --- | --- |
| NONE | 截止前、未取消且有名额可申请，生成独立applicationId → PENDING |
| PENDING | 本人撤回 → WITHDRAWN；发起人拒绝 → DECLINED；批准 → CONFIRMED；截止或整场取消 → EXPIRED |
| WITHDRAWN / 个人退出CANCELLED | 截止前且有名额可重申，生成新轮次并重新审核；历史记录不覆盖 |
| DECLINED | 本场不可再次申请；可浏览其他场次 |
| EXPIRED | 本轮关闭，不允许在已截止或已取消饭局重开 |
| CONFIRMED | 开饭前可退出并释放本人席位；不等于退群。开饭后更正实际出席走饭后报告或支持流程 |

同人同场最多一个有效申请/席位；重试同一次提交不创建新轮次。统计申请按applicationId，参与人数按userId+mealId去重；保留每轮审核、确认和退出时间。

整场取消仅由发起人在开始前主动操作或系统按成团规则触发，终态不能改回OPEN。确认弹层说明影响全部成员、关闭待审申请、通知发起人和所有当前申请者/已确认成员，保留既有聊天。主动取消原因host / booking / other；自动人数不足为insufficient；历史未记录原因是unknown，不能推断原因。发起人负责联系餐厅取消预约；首期无平台退款。开饭后不允许取消掩盖已发生的参与事实，异常通过支持受理。

### 0.4 群聊、私聊与授权

- Inbox可显示待审进度，但PENDING、DECLINED、WITHDRAWN、EXPIRED不授予群聊。首次获准即入群，无二次审批。历史已入群者后续退出饭局仍保留群成员身份。
- 参与退出、独立退群、发起人解散群聊为三个不同动作。饭局结束、整场取消、预约失败/取消均不自动只读。主动退群或解散均需确认，不改变席位或出席资格；发起人解散后不再有成员可发言。
- 退群者只读截至退出时已授权历史，不接收新消息；解散后所有成员只读截至解散的历史。先前未入群者不能读取。若后来重申获准，可重新入群，只能读历次授权区间，退群空档的消息不可见；解散群不能重新开放。
- 私密再约按人形成持续联系，须有一场双方均有有效出席的共同饭局。单方选择保密，双方选择后才开放私聊；互选不影响其他联系人。
- 任一方随时撤回即清除该人对的双方同意，历史私聊只读；重新联系需要双方重新选择，选择发起仍须有窗口内的合格共同饭局。拉黑同样清除双方同意；解除不恢复旧同意。拉黑不改变共享群成员关系，安全问题走举报/退群。
- 每次发送重算授权与出席依据；资格被纠错为无效后暂停仅依赖该场的连接，有其他有效共同场次及双方授权的关系不受影响。历史消息与未来发送权限分别判断。

### 0.5 出席、反馈、修订与指标

- 首期计划结束scheduledEndAt = startsAt + 2小时，不表示实际聚餐被强制终止。从计划结束到其后7天（end ≤ now < end+7天）允许本人报告/更新出席，发起人可补报开始资格名单。本人报告present/absent优先；本人未报告才取发起人，均未报告为unknown，不推断absent。
- 不建立常规冲突核实状态：保留各来源历史和修改时间供审计，结果唯一按本人优先计算。逾期纠错由支持人员依据个案追加带原因、操作者和时间的修订；该修订优先于过期报告，用户不能直接覆盖，后续再纠错仍走支持流程。
- 本人有效present且在开始资格名单才能提交整场体验；个人公评/再约还要求被评价对象亦为同场有效present，不能自评。资格未知时展示原因和报告入口，不开放提交。
- 私密整场体验自愿填写，只收本顿饭的score=1–5整数；同人同场upsert、保留版本。饭后页不询问是否再参加Fancy，不填写产品级原因。
- Settings → Product survey为独立可选产品问卷：again为Yes / No / null，默认null；reasons可多选company / conversation / coordination / expectations / venue / cost / other，可空但去重。至少回答again或选一个原因才可保存；支持清除again及更新答案，不把未答当No。按userId保留最新版本及submittedAt，不绑定mealId，不要求出席，不受饭后7天窗口限制。
- 后台问卷指标先取截至asOf每人最新有效版本，再按该版本submittedAt纳入所选日期；不回捞日期范围内的旧版本。日期与用户分群生效，饭局维度不作用于问卷。整场评分按饭局/资格单独计算，不用产品原因切分饭局评分，不把问卷归因到某顿饭；旧meal.again/reasons保留历史，不自动迁移。
- 公开个人文字评价、私密个人再约、整场体验为独立对象；不从「不想再见某个人」推断「不愿再参加Fancy」。公开评价维持双方提交或7天后发布，不公开单方再约；整场体验仅本人及授权分析/支持人员按职责可读，不向同桌或发起人公开。
- 出席、单场体验及个人评价/再约的自助提交/修改以同一7天窗口为准；独立产品问卷不受此窗口限制。资格纠错后，失效公评不再公开，体验退出有效统计，单方再约不能继续产生授权；原始记录保留修订历史，资格恢复重新计算，不重复计数。
- 申请→出席在计划结束满24小时（asOf ≥ scheduledEndAt+24小时，即startsAt+26小时）进入结果观察。成熟不是冻结：7天内补报与获准纠错影响新快照，旧snapshot保持原asOf内容。整场取消不产生新出席/反馈资格。

### 0.6 游客、支持、账号与验收边界

游客可读Discover地图/列表/筛选、饭局详情、公开主页和已发布个人评价；公开投影只含公开昵称、头像、介绍、兴趣、语言、可选背景及公开饭局信息，不含邮箱、联系方式、申请留言、私密偏好、完整行程历史、消息或报告。申请、发起、Meals、Inbox、本人资料修改、出席及反馈需登录；登录完成返回原操作。iOS深链与Web直接链接沿用同一权限。

举报提交成功返回回执和「已收到，将核实」提示，不宣称已处理。创始人负责真实支持受理，举报提交者可查询本人的处理状态，受理/处理中/已回复分开；通知不含举报正文。紧急情况提示使用当地紧急服务，不由Demo假冒应急响应。

账号删除由本人经重新认证提交，显示受理状态；先撤销登录会话和新的参与/联系权限，未开始主持场次取消、参与场次退出，已开始场次保留其他成员资格，个人公开资料和内容去标识。依法或争议处理必须保留的最小记录仅授权支持可读，保存与清理政策在上线前完成审核与执行验收；不把最终法律文本和真实删除作业伪装成本轮Demo完成。首期不提供导出入口。

验收必须区分：已确认决策、已更新PRD、Demo已表达、测试已通过、跨端规则已对齐、真实开发完成、已发布。此次只交付需求与本地交互表达；SDK、真实认证、服务端事务/鉴权/调度、消息传输、外部支持和原生iOS实现留待研发。


## 1. 需求背景与产品定位

### 1.1 背景与问题
伦敦的国际居民、新移居者及忙碌职场人士可能缺少能同时协调时间、预算与餐厅偏好的同伴。传统聊天需要反复商量，陌生人社交又存在目的不清、背景不了解、怕尴尬、失约和费用不透明等阻力。餐厅预约进一步要求提前确认人数与时间。以上是讨论形成的问题假设，尚未经过访谈或市场规模验证。

### 1.2 产品定位
将本来就要吃的一顿饭，变成认识新朋友的机会。面向在伦敦生活的成年人，以吃饭为场景建立日常社交连接；networking 与 dating 是可能的附加结果，不是默认目的。首发城市伦敦，面向不同国籍与文化背景；全球用户不意味着首轮同时运营全球城市。

已确认 Slogan：**吃个饭，认识一下。 / Meet new people over a meal.**

核心价值：帮助用户找到合适的一顿饭、在见面前形成合理预期、低成本完成协调，并让舒服的一次见面有机会延续。

### 1.3 品牌与文案（2026-10-17 确认）
- 暂定品牌名：**Fancy**。取自英国日常邀约语境 Fancy a bite?，强调“随口约一顿”。单独名称也可能有高档或恋爱联想，需通过餐食与友情场景明确定位；语言含义成立不等于注册可用。
- 品牌 Slogan：**Meet new people over a meal. / 吃个饭，认识一下。** 用于官网、应用商店及产品介绍。
- 邀约文案：**Fancy a bite? / 一起吃点？** 用于 App 首页、推广海报及活动邀请，不替代品牌 Slogan。
- 2026-10-18：Demo 品牌已迁移至 Fancy，开屏、字标、欢迎/发现页邀约、浏览器与分享元数据保持一致。仓库名称及既有分享URL保留 Grab-in-London 标识，不代表界面仍使用旧品牌。

### 1.4 社交价值与增长边界
- 当前以自由约饭切入：用户可选择任何餐厅，自主发起或申请饭局，不限于合作商家。伦敦起步，未来可跨城市。
- 目标是认识合拍、靠谱、有机会长期交往的朋友，不以功利性生意伙伴或恋爱匹配为主要承诺。合拍来自兴趣、语言、预算及交流期待；靠谱来自守时、履约与尊重边界等实际行为。
- 职业、专业、学校等可选填并作为了解经历与话题的参考，不按学历、财富或身份排名；不设置资产展示或考核。付费身份不代表人更优质。
- 朋友熟悉后转到其他平台交流是成功结果；平台持续价值在于新的见面机会与活动。Inbox 承接邀约、饭局沟通及互选联系，不以强留聊天或替代既有通讯工具为目标。
- 初期由创始人与种子用户组织饭局建立供给，不意味着必须长期依赖官方活动运营。

### 1.5 商业模式（方向确认，收入假设待验证）
| 方向 | 付费对象与价值 | 阶段与验证边界 |
| --- | --- | --- |
| 主线：商家活动与引流 | 餐厅为专门活动的推广、组织支持或核实到店结果付费 | 先建立局部活跃用户与饭局供给，再试点；收费方式、价格、归因与履约成本待验证，不以总注册量代替到店价值 |
| 个人端：按次服务试验 | 委托组局、个性化社交练习等额外服务 | 基本发现、发起、申请、必要资料查看、群聊与互选联系免费；基础筛选推荐不作为付费优势。先测试按次购买，有重复购买后再考虑会员，不承诺月费或交友结果 |
| 后续：组织者服务 | 社群主理人持续招募与管理饭局的工具 | 有稳定需求后再验证，不作为首版承诺 |

商家活动须明确标识；付费推广与个性化适合理由区分。官方精选组局可由平台或认可组织者试验，非当前主营承诺；霸王餐、折扣等是商家营销福利，不作为稳定会员价值。订金不是平台收入。商家收入建立前存在冷启动投入期，收入规模与单位经济尚未验证。

### 1.6 Ask Fancy Demo 与长期 AI 方向（长期方向非已实现需求）
- 长期愿景为懂用户的社交伙伴；当前围绕约饭探索理解期待、寻找饭局、破冰与表达支持、代理组局协调。用户保留选择与建立关系的主动权。
- A2A 指授权范围内由 Agent 协商时间、地点、预算等见面条件，真人决定是否参加；不以 Agent 彼此聊得来推断真人合拍，不绕过互选边界批量私信。协议、授权与实现方案尚未确定。
- 以满意的真实见面、愿意再见及关系延续衡量价值，不以 AI 陪聊时长作为主要成功指标。实时对话分析、翻译与提醒仅为探索，未决定录音或上线方案。
- 先验证约饭，再考虑运动、戏剧等共同体验；真实活动关系可能形成熟人圈与朋友的朋友连接，用户规模增长不自动等于熟人社交。当前不以接入 WhatsApp、Instagram 或接管既有朋友圈为前提。
- 当前Demo已恢复Ask Fancy浮动助手：自然语言查找/比较示例饭局、费用解释、申请/群消息/创建饭局草稿和My preferences。沿用原浮动拖动、贴边收起、助手首页、30分钟闲置会话重置；保存偏好需确认，支持修改/删除。草稿只带入原编辑器，申请、发布、发送仍由用户审核并主动提交，助手不能绕过登录、host批准、截止或群聊权限。语音只在浏览器支持且用户确认说明后请求，识别结果可编辑且不自动发送；不支持/拒绝可继续打字。
- 以上是本地确定性示例解析，不是大模型或真实推荐、消息、餐厅服务；刷新/重置清空当前会话及偏好。A2A、实时翻译、商家与组织者能力均未实现，不得视作真实 R1 已承诺范围。后续需验证用户价值、付费意愿、供给与成本，再形成具体需求和验收。

### FR-09 Inbox、饭局申请与群聊权限（P-05/P-08/P-14）

首期：群聊独立生命周期与联系人授权按§0.4。


**当前交互**：Inbox分Chats与Applications两个tab，各有数量与空态。Track in Inbox直接进入Applications。Chats收纳已授权群聊与个人会话。导航当前页图标使用填充色并带aria-current。群聊发言头像可进入对应公开主页，返回保留原会话。群设置入口展示成员、Host/Member/You身份；成员可退群，host可进入饭局管理及解散，动作移出聊天正文。只读群无新的退群/解散动作。成员管理不增加踢人或更名权限。

**原则**：Inbox是申请进度、待办和已开放会话的入口；出现在Inbox不等于已经入群。是否可入群取决于饭局的确认席位。发起人批准申请就是入桌/入群授权，**不再增加独立的入群审批**。有预付时还须付款成功；无预付则批准即确认。

| --- | --- | --- | --- | --- |

**与预约的关系**：餐厅PENDING或FAILED不阻止已确认成员讨论安排；不能因为餐厅CONFIRMED就让申请中的用户入群。预约失败时可讨论重选，整场取消也不自动归档；仅退群或发起人解散导致只读。私聊继续使用饭后双方互选规则，host批准饭局不自动开放一对一私信。

**输入/输出**：mealId、membershipState、wasConfirmed、bookingState、消息内容1–2000字符、消息预览偏好 → 申请卡/待付款卡/群会话/只读归档，以及read/write权限。预览显示本饭局发起人和最后一条已发消息；关闭预览后列表仅显示Message previews are hidden，会话内部内容不删除。

**交互路径**：Apply→申请状态页的Track in Inbox→Inbox待审核卡→Preview host approval→待付款卡（或现场付直接群会话）→付款→Inbox群聊→发送消息。所有Preview均标识模拟，不代表真实host操作。多场饭局分别按mealId更新，操作一场不得改变另一场的申请或人数。

**边界校验**：未确认者不得读取成员消息或发送；隐藏按钮不是权限控制，未来后端订阅/历史读取/发送接口都验证成员资格。批准/支付失败或撤回不产生群成员关系。重复确认不重复计数。退出时取消实时订阅并冻结其可读历史，未来服务端必须按退出时间截断，不允许读取退出后的新消息。Demo以本地历史快照和独立确认记录模拟，刷新清空。消息空白禁止发送；已有模拟发送失败/实时同步能力仍未接入，不能宣称真实跨设备聊天。

### FR-10 饭后反馈、互选与举报（P-11）

- 饭后页移除无操作含义的大心形装饰，只保留一个出席问题标题；规则说明收进信息按钮。单场只收1–5评分；再次参加Fancy与产品原因移到Settings问卷。Past饭局头像与Leave feedback至少20px间距。
- 注册和Edit profile共用选项：伦敦状态单选标签，完整语言名称单选下拉，兴趣多选标签；保存后主页反映新内容，取消不保存草稿。

首期：出席资格、整场体验与7天窗口按§0.5；公开个人评价与私密再约保持独立。

- 输入：已完成饭局且实际同桌关系、公开文字 0–500 字符、私密再约意愿、私密举报原因。
- 输出：评价提交状态、待双方发布/已发布、互选提示、私聊入口或举报确认。
- 操作：公开反馈与愿意再约分别选择；无公开个人综合星级；首期独立私密整场评分见§0.5；Demo 默认7天评价期，双人互评提交或期限结束后发布；群局按有实际同桌关系的评价双方计算。可单独私密举报，不要求先公开差评。
- 边界：未出席不能评价；不能自评；重复提交不重复记录；单方再约意愿不披露；拉黑优先阻止联系；新用户暂无评价；举报提交不等于平台已处理。Demo 通过显式按钮推进“饭局结束”与“对方也愿意”，不能伪装真实他人行为。

## 8. 前后端接口与输入输出契约（目标设计）

Demo 不调用以下真实接口，前端状态模拟提供等价交互。正式接入时由服务端重新校验权限、席位、报价及外部结果。

| 接口 | 输入 | 成功输出 | 关键失败 |
| --- | --- | --- | --- |
| GET /v1/meals | date、area、budget、size、language、cursor | items:MealSummary[]、nextCursor、mapGroups | 参数非法422 |
| GET /v1/meals/{id} | mealId、session | detail、allowedActions、version | 不可见404 |
| POST /v1/meals | CreateMealInput、Idempotency-Key | 201 Meal | 资料不足422、时段失效409 |
| PATCH /v1/meals/{id} | patch、expectedVersion | 更新后Meal | 非host403、版本冲突409 |
| GET/PATCH /v1/profiles/me | 资料字段 | 私有本人资料/保存后公开投影 | 字段422 |
| GET /v1/profiles/{id} | subjectId | PublicProfile | 已拉黑或不可见404 |
| POST /v1/meals/{id}/applications | message、intentKey | 201 Application | 重复409、已满409、已截止409 |
| PATCH /v1/applications/{id} | decision、expectedVersion | Application、holdExpiresAt | 无权403、无位409 |
| POST /v1/applications/{id}/payment-intents | quoteVersion、intentKey | paymentId、dueNow、status | 席位过期409、价格变化409 |
| GET /v1/payments/{id} | paymentId | Payment、refunds | 非本人403 |
| POST /v1/meals/{id}/reservations | slotId、partySize、intentKey | Reservation | 无位409、供应商未知202 |
| POST /v1/meals/{id}/cancellations | reason、termsVersion、intentKey | cancellation、refundQuote/status | 条款变化409 |
| GET/POST /v1/conversations/{id}/messages | cursor / text、clientMessageId | messages / Message | 非成员403、过长422 |
| POST /v1/meals/{id}/reviews | subjectId、text、intentKey | Review、visibility | 未同桌403、重复409 |
| PUT /v1/meals/{id}/reconnect/{userId} | wantsReconnect | mutual:boolean | 未同桌403、拉黑403 |
| POST /v1/reports | subjectId、mealId?、reason、detail | reportId、received | 无效422 |

统一错误：`{ error: { code, message, fieldErrors?, requestId } }`；400格式、401未登录、403无权、404不可见、409状态冲突、422字段、429限流、503依赖不可用。不要返回支付密钥或内部堆栈。

示例申请输入：`{ "message": "New to London and would love to join.", "intentKey": "apply-demo-001" }`。
示例输出：`{ "id": "app-001", "status": "PENDING", "occupiesSeat": false, "allowedActions": ["WITHDRAW"] }`。

支付/预约/退款目标可靠性：同一意图重试复用幂等键；原子占位并校验载荷；处理中重复返回202或409约定状态；外部回调签名校验与去重；未知结果对账，禁止盲目再扣款/再订；跨服务取消采用补偿与人工异常队列。本轮只演示可见状态，不声称具备交易可靠性。
