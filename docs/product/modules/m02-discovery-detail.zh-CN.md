# M02 发现饭局与查看详情需求说明

需求修订：r05｜状态：产品需求草稿。

## 为什么需要、谁使用

用户需要先判断时间、地点、人数和预算是否合适，再决定是否申请；浏览过程应保留选择上下文。

使用者：访客、登录用户、该饭局发起人。

本版适用端：iOS App。 产品背景、功能范围与产品角色见[整体MVP需求](../fancy-requirements-baseline.zh-CN.md)。

## 用户从哪里进入、怎样完成

入口：从Discover地图/列表进入，或打开公开饭局链接；返回原浏览位置。

1. 用户选择日期、人数及必要筛选，在地图或列表看到同一批匹配饭局。
2. 打开区域卡片或列表项，查看餐厅、伦敦当地时间、人数、预计人均预算与发起人公开信息。
3. 查看完整饭局详情，了解申请状态、可操作动作及不可申请原因。
4. 用户主动选择申请时交给M04；登录不足时交M01，完成后返回同一mealId。
5. 返回发现页恢复已应用筛选、区域和当前项，不用从头查找。

## 必须保持的业务规则

- 日期多选内部取或、不同字段取交集；筛选草稿只有明确应用后生效，关闭不改变已应用结果。
- 人数为含发起人的总人数，不是剩余席位；区域标记数字为匹配饭局数量。
- 游客只读公开字段；不暴露邮箱、申请留言、完整行程、群消息或私密偏好。
- 未知菜系/饮食不推断，预计预算不代表收款或过敏安全；餐厅信息不证明已有订位。

## 失败、返回与取消

- 无结果提供明确说明及清筛选入口；查询失败和无结果分别表达，不保留误导的旧卡片。
- 详情打开后状态可能变化；满员/截止/取消/开始等按最新事实限制申请。
- 对象不存在或无读取权限时说明不可用，不从缓存泄露旧内容。

## 版本范围与可观察验收

### D02 发现与详情闭环

范围与终点：找到一场合适饭局、读懂参加条件、进入申请入口并能原路返回。


- D02-AC01：同一筛选下地图、列表和区域计数一致；关闭未应用的筛选不改变结果，空结果有清除条件入口。
- D02-AC02：打开详情再返回保留位置；访客只能看到公开信息，不暴露申请留言、邮箱或消息。
- D02-AC03：满员、截止、取消、删除或不可访问时，主操作及原因准确，登录回来仍需本人主动申请。
