# M02 发现饭局与查看详情需求说明

需求包修订：r02｜文档性质：项目协调负责人的模块需求输入｜状态：待用户审阅，未签发实施工作包。

## 为什么需要、谁使用

用户需要先判断时间、地点、人数和预算是否合适，再决定是否申请；浏览过程应保留选择上下文。

使用者及职责：访客、登录用户、饭局发起人；详情动作随本人身份及饭局权威状态变化。

适用端：移动Web与iOS。背景、术语、规则权威及授权见[整体需求基线](../fancy-requirements-baseline.zh-CN.md)。本说明写用户结果，详细字段/接口由对应产品经理和研发人员按原规则展开；不以现有代码反推需求。

## 用户从哪里进入、怎样完成

入口：从Discover地图/列表进入，或打开公开饭局链接；返回原浏览位置。

1. 用户选择日期、人数及必要筛选，在地图或列表看到同一批匹配饭局。
2. 打开区域卡片或列表项，查看餐厅、伦敦当地时间、人数、预计人均预算与发起人公开信息。
3. 查看完整饭局详情，了解申请状态、可操作动作及不可申请原因。
4. 用户主动选择申请时交给M04；登录不足时交M01，完成后返回同一mealId。
5. 返回发现页恢复已应用筛选、区域和当前项，不用从头查找。

## 必须保持的业务规则

- 日期多选内部取或、不同字段取交集；筛选草稿只有明确应用后生效，关闭不改变已应用结果。
- 人数为含发起人的总人数，不是剩余席位；区域标记数字为匹配饭局数量。
- 游客只读公开字段；不暴露邮箱、申请留言、完整行程、群消息或私密偏好。
- 未知菜系/饮食不推断，预计预算不代表收款或过敏安全；餐厅信息不证明已有订位。

## 失败、返回与取消

- 无结果提供明确说明及清筛选入口；查询失败和无结果分别表达，不保留误导的旧卡片。
- 详情打开后状态可能变化；满员/截止/取消/开始等按最新事实限制申请。
- 对象不存在或无读取权限时说明不可用，不从缓存泄露旧内容。

## 版本范围与可观察验收

### D02 发现与详情闭环

范围与终点：找到一场合适饭局、读懂参加条件、进入申请入口并能原路返回。

前置需求版：本模块最小共用服务；无其他需求版整体验收前置。

- D02-AC01：同一筛选下地图/列表/区域计数一致，零结果允许应用，关闭未应用草稿不改变结果。
- D02-AC02：从详情返回保留筛选与位置；公开链接访客可读同一饭局且无私密字段。
- D02-AC03：满员、截止、取消及删除对象的实际动作/原因正确；登录回流与D01联合验证。

## 依赖、职责与不做事项

模块交接：向M04传mealId与来源上下文；向M03复用餐厅读取，向M10提供公开详情投影。

本模块不做：直接申请、发起饭局、分享渠道、AI排序、实时定位导航新增能力。

最小测试前置：公开饭局集合、真实餐厅服务适用配置及空/失败状态；浏览可先做受控验收，真实Places门槛保留。

上述验收是需求条件，不是已经执行的结果。受控测试、实际浏览器/设备、真实服务及联合旅程分别记录；原要求中的真实门槛未齐必须保留阻塞。一次模块验收不代表发布批准。
