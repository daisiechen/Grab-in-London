# M04 申请参加与成员管理需求说明

需求包修订：r02｜文档性质：项目协调负责人的模块需求输入｜状态：待用户审阅，未签发实施工作包。

## 为什么需要、谁使用

想参加的人需要明确表达申请并知道是否获准；发起人需要安全选人、控制名额，双方都能辨认退席与退群。

使用者及职责：申请人、该饭局发起人；不同用户不能互相代审。

适用端：移动Web与iOS。背景、术语、规则权威及授权见[整体需求基线](../fancy-requirements-baseline.zh-CN.md)。本说明写用户结果，详细字段/接口由对应产品经理和研发人员按原规则展开；不以现有代码反推需求。

## 用户从哪里进入、怎样完成

入口：详情Apply入口、本人Meals状态、主持人的Manage applications。

1. 申请人读详情后填写介绍并主动提交；资料不足先补全，原留言保留。
2. 看到Pending及撤回入口，等待中不占席位也不获得群聊。
3. 发起人查看申请及公开主页，在有名额且未截止时批准或拒绝。
4. 批准后直接Confirmed并入群，不走订金支付或二次审批。
5. 用户可在开饭前退出席位；本人撤回/退席后符合条件可新一轮申请，始终显示当前轮次。

## 必须保持的业务规则

- 同人同场最多一个有效申请/席位，重试同一次请求不生成新轮次；Pending不占位。
- 批准与退出原子校验容量及截止；now≥closesAt停止申请和审批。
- 被拒绝本场不可重申；过期申请不重开；主动撤回/退席的重申须新轮次审核。
- 个人退席仅释放本人席位，不等于退群；整场取消由M03负责，不能把退席按钮接成取消全场。

## 失败、返回与取消

- 提交遇满员/截止/失败显示原因并保留留言；请求结果未知先找回原意图。
- 最后一席并发审批只能一人成功；另一申请仍有准确状态，不显示虚假Confirmed。
- 登录/权限失效后停旧重试；离开再打开的新稿不被旧响应清除。

## 版本范围与可观察验收

### D04 申请与成员闭环

范围与终点：第二个用户完成申请→审批→确认→退出/重申，名额及状态始终一致。

前置需求版：D01、D02、D03。

- D04-AC01：正常申请/批准无需付款，未批准账号读不到群聊，批准后身份及席位一致。
- D04-AC02：最后名额并发、精确截止与重复请求不超卖/不重复申请。
- D04-AC03：撤回、退席、拒绝与过期分别按规则显示重申资格；退席后既有群身份不误删。

## 依赖、职责与不做事项

模块交接：本模块拥有申请轮次和席位事实；M03据此判断成团，M05据批准事件授群权限。

本模块不做：收费保留位、支付、修改餐局安排、主动退群和群解散。

最小测试前置：两名申请人和发起人、可控截止、并发请求入口；M05最小群成员契约，无须推送服务。

上述验收是需求条件，不是已经执行的结果。受控测试、实际浏览器/设备、真实服务及联合旅程分别记录；原要求中的真实门槛未齐必须保留阻塞。一次模块验收不代表发布批准。
