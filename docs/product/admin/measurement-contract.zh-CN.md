# 首期运营指标与采集契约 v4

日期：2026-10-20。本文是[后台 PRD](PRD.zh-CN.md)的研发附录；共享业务规则以[主 PRD](../PRD.zh-CN.md)为准。覆盖后台全部指标，不把原型内存状态当作生产埋点。当前入口表达以主PRD §0与用户端本轮验证为准；生产采集 SDK、业务服务、鉴权和数据管道仍待接入。

## 1. 每周要作出的决定

首期保留三项结果：每周确认出席用户数、首次申请后14天内出席率、首次出席后30天内再赴约率。每周由产品负责人复核，运营负责人处理招募、响应和体验问题；不设无基线的增长目标，不从小样本生成因果结论。

| 问题 | 结果/诊断/护栏 | 可采取的行动 | 节奏与限制 |
|---|---|---|---|
| 真实见面规模有无增加？ | 每周确认出席用户数；同时看出席结果记录覆盖率、未知/来源不一致人次 | 补齐记录后，再决定是否扩区域或调整供给 | 每周；首尾部分周不与完整周直接比较 |
| 想参加的人在哪一步受阻？ | 发现无结果请求数/请求率；加载→看到卡片→详情的人数；7天申请率；申请、批准、席位确认及出席 | 先按区域、语言、预算、人数定位供给，再看详情与申请门槛 | 每周；行为人数不与申请记录数跨单位相除 |
| 为什么约不成？ | 开始前招募达标率、取消率及原因；审核50%/90%用时、待审数量与最久等待；创建开始→安排→发布及字段错误 | 调整招募时点/人数、简化创建、改善host响应提示 | 待审每天看；审核只看已处理会漏掉一直未处理的人 |
| 体验问题具体是什么？ | 单场1–5分布、评分覆盖；设置中的整体体验问卷意愿与因素 | 单场评分定位体验分布，产品问卷因素指导整体产品访谈，不归因某顿饭 | 每周；未反馈/未填原因单列；多选原因不相加成100% |
| 是否值得再来？ | 30天内再赴约率、各首次出席周样本与观察中人数；后续可申请饭局曝光比例 | 区分暂无完整观察窗口、未看到后续机会、看到但没再来；结合反馈验证 | 每周追踪，完整30天后判断；早期不以意愿代替真实回访 |
| 数据可靠吗？ | 必填字段缺失、重复事件、接收延迟、测试/员工分类与出席覆盖 | 修复采集/身份映射，追溯来源差异；不能用补零填空白 | 日常；数据故障阻止业务结论 |

低优先级：不增加DAU/停留时长/点赞排名、增长活动、商家/财务/客服模块和自动经营Agent。功能使用人数仅作为问题定位的辅助，不占概览主指标。没有真实数据基线，不设置红黄绿业务阈值或自动优先级。

## 2. 先统一用语

- **申请提交成功**：服务器成功创建申请记录，不代表host批准。
- **获准**：host第一次有效批准。拒绝也属于有效审核，纳入审核用时。
- **席位已确认**：进入确认名单；首期线下各自付款，获准即可确认；预付仅后续参考。与餐厅订位独立，也不代表实际出席。
- **确认出席**：饭后具有有效出席报告，且用户本来在本场应确认名单中。不得由打开群聊、付款、席位确认或未取消推断。
- 不再称“成熟用户”。**观察满14/30天**是从该用户的首次申请/首次出席时间，到数据截止时间已完整经过14/30×24小时，与年龄、活跃或熟练程度无关。
- **首次申请发生在所选日期**：先从完整历史找到每人第一笔有效提交，再按这个时间筛选。例如选9月1–30日，分母候选是首次申请在9月的人；10月发生的后续出席仍可用于观察，但必须在14天内且不晚于数据截止。
- “申请+出席”是按同一userId关联两类权威记录，同时满足时间、成员资格、未取消/未提前退出及有效出席条件。不是把两个点击事件相加；首次赴约可以是另一场饭局。

例：用户10月1日12:00首次申请，10月10日出席；10月12日截止时仍在观察，不进入14天指标分子或分母；10月15日12:00后计入分母，同时计入分子。另一用户10月16日首次出席，到11月15日相同时刻才具有完整30天观察期。历史曾以host身份先出席、后来首次申请的人仍有首次申请记录，但不满足“首次出席发生于首次申请之后”的分子条件；回访价值看实际首次出席队列。

| 数据 | 现有/本轮入口与状态 | 生产获取方法与权威 |
|---|---|---|
| 注册时间、稳定userId | 现有注册流程为本地原型 | 账户服务创建成功；服务端生成去标识ID，不用昵称/邮箱去重 |
| 发现筛选、结果数量 | 现有Discover列表/地图及筛选；尚无采集SDK | 发现服务每个成功请求返回requestId、完整筛选及eligibleCount；客户端记录列表实际呈现。报错另记discovery_failed；不当0结果 |
| 实际看到卡片 | 现有饭局卡片；尚无可见性采集 | 客户端IntersectionObserver，卡片至少50%面积可见且连续1000ms、页面前台；不可申请/自己发起/已满/取消/已开始的卡片不发有效曝光；暂停/移出重置计时。每sessionId+mealId只留首次有效曝光；保存visibleRatio/durationMs、当时eligible=true及时间 |
| 详情、资料、筛选、地图、群聊行为 | 现有导航和表单；尚无采集SDK | 页面实际呈现/筛选生效后发事件；群聊记录打开成功，不记录聊天正文 |
| 创建尝试与校验卡点 | 现有四步创建 | 客户端每次新建草稿生成attemptId；开始、Arrange通过、字段错误；后端发布成功带同attemptId。刷新新建尝试，重试复用同事件ID |
| 申请、审核、席位、退出 | 申请/host审核/退出/整场取消的本地原型；首期不经过支付 | 业务服务保存applicationId、userId、mealId、appliedAt、第一次有效decidedAt及decision、confirmedAt、withdrawnAt、版本。不得使用按钮点击代替成功 |
| 最低成团人数、是否招募达标 | 创建minimum与capacity，整数2≤minimum≤capacity≤6且含host；预算min/max另存 | 发布保存capacity与minimum快照；服务端每次确认/退出追加名额变更，从开始前历史求peakConfirmed（不含未付款者）。招募达标只表示历史峰值，截止与之后人数检查按主PRD §0.2另产取消事实，不由分析层推断取消 |
| 场次是否结束 | 用户端当前依靠历史样例或验收推进；生产尚无调度 | 首期计划结束时间=开始后2小时，发布保存scheduledEndAt（后续可独立改规则）。到时才开放出席报告，不把到开始时间就当结束。后台endsAt取该字段；旧fixture缺值才使用开始+2小时兼容 |
| 本人是否实际出席 | **本轮新增**：Meals→Past→饭后页→I attended / I did not attend | 服务端校验已结束、未取消、在开始前确认且未提前退出；self来源、subjectId=actorId、reportedAt、版本、幂等键 |
| host记录每位成员出席 | **本轮新增**：已完成的host饭局饭后页→Guest attendance逐人记录 | host仅本场名单；包括host本人自报；无默认“全员出席”，不强迫一次填全。host与self各留最新版本，本人优先、host补缺；来源差异保留，逾期支持个案纠错优先且审计，不覆盖原报告 |
| 单场饭局评分 | 饭后页私密MealExperience，只有1–5分 | 出席资格有效，end≤提交<end+7天；按userId+mealId版本化upsert，只要求score，不再要求意愿和因素 |
| Fancy整体问卷 | Settings自愿ProductSurvey，登录即可提交 | 按userId保存版本、submittedAt、again(bool/null)、reasons七枚举；至少回答again或选因素，不绑定mealId/出席/7天窗口；历史单场旧字段不迁移 |
| 测试/员工身份 | **本轮新增**：后台数据与定义→统计账号分类→userId+正式/测试/员工 | 生产仅data-admin；服务端保存分类历史、操作者、理由、时间、版本；业务请求和事件关联可信分类，不允许客户端自称正式。Demo会话内重算、刷新恢复；生产变更重建历史快照，旧snapshot保留 |

当前 Demo 两端各有独立本地状态，不会把App点击直接传给后台fixture；生产采集接通后，以上业务事实来自同一服务，客户端事件由独立采集入口进入。同一前端入口存在不代表已有生产数据。后台页内的来源/质量页集中呈现连接状态，常规页面不重复“模拟数据”横幅。

## 4. 每项指标的统计逻辑

通用：事件按eventId去重，业务申请按applicationId，参与人次按(userId,mealId)，用户按userId，饭局按mealId。采用统一快照asOf，同时要求occurredAt和receivedAt≤asOf。以伦敦日期做入组筛选，连续观察时长用UTC毫秒。先查全历史首次，再筛选日期。零分母=null，显示—；所有比率带分子分母，未满观察期不纳分子也不纳分母。数据不可得显示未就绪，不使用fixture补齐。

| ID/页面 | 分子或数值 | 分母/入组与获取 | 排除与边界 |
|---|---|---|---|
| weekly/概览 | 该周有present事实的去重userId，含host；同周多场一次 | 按meal.startsAt归周，周一开周；参与关系+出席报告 | 已结束未取消；unknown不入数；来源差异按本人优先计算；首尾周可能不完整 |
| activation/概览、留存 | 历史第一次有效出席时间在历史首次提交申请后0–14天内的用户数 | 首次申请日期在筛选范围且appliedAt+14天≤asOf的用户数 | 纯host不算申请，单看创建路径。首次出席可跨场次/区域；缺历史时标可观测首次 |
| retention/概览、留存 | 分母用户中首次出席后(0,30天]内出席另一mealId的人数 | 历史首次出席时间在范围且+30天≤asOf；按首次出席周分组 | 同场重复不算回访；后续不限入组区域/语言/来源；观察中人数单列 |
| coverage/概览、供需 | present+absent参与人次 | 开始日期在范围且已结束未取消的应确认人次（host+开始前已确认未提前退出者） | 本人优先、host补缺；来源差异仍可计分子；逾期支持纠错优先；未知绝不算未出席 |
| discovery/供需 | resultCount=0的有效成功请求 | 所选发生日期、请求筛选匹配的有效discovery_results请求 | 缺/非法resultCount隔离，error不进分母；每次成功刷新是新请求，重试同ID不加数 |
| 浏览人数/旅程 | 加载成功/有效曝光/详情呈现各自去重身份数 | 分别取discovery_results/meal_impression/detail_view在所选发生期的记录 | 三种期内人数不必嵌套，不能跨行当严格漏斗。匿名只经当前授权会话明确映射 |
| discovery7/旅程 | 分母用户任一观察满7天的发现加载之后7天内提交成功申请的人数 | 至少一次加载在范围且occurredAt+7天≤asOf的去重用户 | 申请可跨结束日期；保留入组业务维度；未知身份不推断已注册 |
| 曝光后7天未申请/旅程 | 分母用户中，没有在任一已满7天的有效曝光后7天内提交申请的人数 | 范围内有效曝光且曝光后已满7天的去重用户 | 用户去重，不把多次曝光当多人；不是点击流归因或体验差的因果结论 |
| 申请→获准→席位确认/旅程 | records数；approved数；confirmed数 | 期内提交成功同applicationId跟踪到asOf；获准有首次审核，席位有confirmedAt | 单位是申请，不是用户；首期获准即确认，不要求二次审批或付款；不要把确认当出席 |
| 申请→出席/旅程 | 关联有效present事实的申请数 | 期内申请且asOf≥scheduledEndAt+24小时的申请数（首期开始后26小时） | 包括被拒、撤回、取消仍在分母；确认成员资格及报告必须有效；覆盖不足时先补数据 |
| 审核用时/旅程 | (第一次decidedAt−appliedAt)/小时的最近秩P50、P90 | 上述期内申请中已有首次有效批准/拒绝，decidedAt≤asOf且≥appliedAt | 待审不入分布；另显示待审数量、当前等待至asOf，退出/过期/整场取消不算批准或拒绝，已终止申请不继续计待审 |
| 创建漏斗/发起 | 有后续create_arranged、其后meal_published的尝试数 | 所选发生期create_started，按identity+attemptId去重并按时间衔接至asOf | 跨期完成仍入原尝试；form_error按固定step/field/errorCode统计事件数，不发送输入值 |
| formation/发起、供需 | 开始前peakConfirmed≥minimum的场次数 | 开始日期在范围且已到开始时间的已发布场次数 | 取消仍在分母；达标不等于实际举行；minimum冻结，非饭局上限 |
| cancellation/供需 | 取消场次数与固定原因分布 | 同上已到开始时间的已发布场次 | 单人退出不算整场取消；insufficient/host/booking/other/unknown，未填写单列 |
| 有出席证据的场次/发起 | 至少一位有效present的不同mealId数 | 已结束场次的参与事实 | 只能声称有证据，不能说全员完整履约 |
| feedback覆盖/留存 | 最新有效单场评分人次 | 确认present人次，按饭局开始日期筛选；提交时间≤asOf | 仅1–5整数有效，同人同场取最新；不读取again/reasons，不读公开reference |
| 单场评分分布/留存 | 1–5各分数份数 | 同一有效MealExperience集合 | 样本=用户×饭局，自选择偏差，不与整体问卷交叉切片 |
| survey意愿/留存 | 最新有效ProductSurvey中again=true的用户数 | 明确回答again=true/false的用户数 | 先按userId取截至asOf最新有效版本，再按submittedAt日期入组；again=null单列，不当No |
| survey因素/留存 | 每个固定因素的选择用户数；未选因素的用户数 | 与意愿同一最新问卷入组集，包含只选因素而again=null者 | 多选不加成100%；未选择不代表无问题，无mealId，不按单场评分或饭局属性切片 |
| 后续机会/留存 | 满30天用户中，首次出席后30天内实际有效看到另一未来可申请饭局的人数 | 同retention分母；曝光必须发生在首次出席之后 | 只是看见机会的代理；没有曝光不代表没有供给，不据此推断匹配质量 |
| 功能使用/旅程 | 地图/筛选/资料/群聊等事件去重身份数 | 期内有效同名事件；仅相关可采集功能 | 没有明确尝试分母不生成完成率；不采集消息内容 |
| 质量/数据页 | 缺必填/重复/排除数量；接收延迟P90 | 全快照原始/有效事件，不受业务筛选 | 质量页展示源连接、asOf与definitionVersion，不伪装实时 |

## 5. 过滤与账号标注

所有分类筛选可多选。同字段OR、跨字段AND，空选=全部；数值条件覆盖完整域。不把选择全部已知值等同于“全部”（未来新值仍须可见）。URL用逗号存集合，旧单值链接仍支持。旧“≤25/≤30”链接保持原阈值语义，新UI仅输出区间。

- 区域/来源取记录当时属性；用户分群只改变人数/参与人次，不改变场次分母。
- 交流语言指**支持这种交流语言**：English或中文。中英双语场次可被两种筛选命中，选择两项按并集去重；不设置“中文/English”混合选项。App现有Mandarin映射Chinese，长期统一languages数组。
- 人数指**总人数上限，含host**；2、3、4、5、6、7及以上可多选，非剩余名额。当前App仅允许2–6，7+用于完整分析域/未来数据，不代表发布范围扩张。
- 预算指饭局预计**人均预算上限**（App的max），不是需预付金额。区间[0,20]、(20,30]、(30,40]、(40,+∞)，外加未填写。£20和£30只落一个区间；选择两个区间取并集。
- 来源未知的事件在选择具体来源时不猜测归类；发现请求的未知语言/预算等不能拿任意饭局补齐。宽范围请求应保留实际请求属性与unknown。
- 账号分类变更不改登录/业务权限。统计统一排除test/staff用户的事件、申请、参与与反馈；其host饭局整场排除，防止测试供给进入场次分母。正式host饭局上的测试成员不计人数，但招募达标也必须从正式确认成员状态重建；不能沿用包含测试成员的历史peak。当前后台按确认时间与退出时间重建开始前峰值，明确排除被标注的成员；生产如有重复申请/多次退出重入，须使用完整席位状态变更日志重建。

## 6. 生产落地顺序与验收

1. 先接入账户分类、饭局、申请/审核/确认/取消服务事实；发布同时保存minimum、scheduledEndAt和预算上限，不以客户端表单作为权威。
2. 接入出席报告与单场评分；另接Settings产品问卷服务。出席自报/host各自幂等更新，保留历史，本人优先、host补缺。上报窗口首期从计划结束到7天后，过期仅授权支持人员按带审计的个案纠错；不自动把未报改未出席。Demo时间推进仅用于验收，不代表线上调度。
3. SDK接发现结果、真实曝光、详情和创建步骤；客户端重试复用eventId，服务端receivedAt，业务成功走事务事件/可靠outbox或增量业务查询。客户端event接口拒绝自报业务成功，业务端保留状态版本。

**数据取得状态**：用户端本轮只表达本地入口和状态；账户服务、发现查询与曝光SDK、业务服务及可靠事件、报告/反馈持久化、支持纠错、鉴权、不可变快照与定时刷新均需研发实现。不以fixture、页面存在或测试通过证明这些已上线。

**快照和晚报**：归属以业务发生时间，进入快照还要求服务接收时间≤asOf。申请→出席从计划结束后24小时才纳入结果分母；例如10月1日18:00开始、20:00计划结束，到10月2日20:00才成熟。10月3日补报可改变新快照，10月2日旧snapshot不改。7天是自助报告/体验修改窗口，不是冻结指标的时间；支持修订也只生成新快照。生产应提供完整版本流，后台本地updatedAt/at只是其已裁定的投影，缺少接收与版本数据不得声称可回放生产历史。

**申请结果防重复**：出席只归到本场开始前有效确认且未提前退出的申请轮次；旧撤回/被拒/过期轮保留在申请分母，不借同用户新轮出席计成功。重复投递按applicationId去重，版本取截至快照的最新合法状态。业务约束同人同场最多一个有效席位。

**运营最小性**：现有五页覆盖供给缺口→申请响应→招募取消→实际出席→体验→再赴约，保留覆盖率与样本作为解释护栏。无需经营分析Agent或新增经营模块；数据检查是规则摘要，由产品负责人每周复核。

版本变更：v4在v3基础上将单场评分与产品问卷分离。页面/CSV同为v4；历史v3的“反馈愿再参加”与v4的“问卷愿再参加”来源、粒度和入组日期均不同，不直接比较增长，也不把旧单场答案迁移为用户新问卷。

## 8. 产品问卷的入组、缺失与导出

1. 数据源为Settings的独立保存成功结果，生产由服务端生成提交时间、receivedAt和单调version；原型入口不证明已接SDK或持久化。业务投影先限制接收/提交≤asOf，按userId取最新有效版本，再按该版本submittedAt伦敦日期和用户分群过滤。
2. 例如9月25日Yes、10月2日No；asOf为10月18日且查询9月，用户不入组，因为最新提交在10月。asOf为9月30日时保留Yes。相同时间由服务端版本序列定先后，Demo以输入序列兼容。
3. again未答为null，No为false。仅选因素可提交；两者全空不可保存；因素去重且仅七枚举。提交人数=入组去重userId，回答人数=again非null，未回答人数=提交−回答；未提交者没有可推断回答，不用总注册量伪造问卷完成率。
4. 区域/来源/语言/人数/预算属于饭局属性，不适用整体问卷。选择这些过滤时问卷样本不变，页面和CSV明确只有日期与用户分群生效。不能将被筛选饭局参与者自动当问卷对象，也不能按饭局星级切片问卷因素。
5. CSV分别导出单场评分覆盖、1–5分布与surveyWillingToReturn、surveySubmittedUsers、surveyUnansweredAgain及surveyFactor:*；问卷单位为用户，评分单位为人次。导出附surveyScope和definitionVersion=4，原因多选只作选择比例参考，不混作互斥评分分布。

隐私：单方互选、公评正文与聊天正文不进入单场评分或ProductSurvey分析；问卷只读取明确提交的固定答案。
