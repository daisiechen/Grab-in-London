# Fancy 产品数据后台 PRD

版本：1.2｜日期：2026-10-19｜状态：已实现独立高保真交互 Demo；真实采集及生产服务待建设。

## 1. 目标与范围

面向伦敦真实约饭试点的内部产品团队，以可信的使用数据指导产品迭代。核心问题：是否找到合适饭局、为什么没有约成、真实见面是否发生、用户是否再次赴约。业务背景沿用[用户端 PRD](../PRD.zh-CN.md)，不改变普通约饭免费、用户自主审核、成员与订位付款状态分离等既有规则。

本轮只建设五个分析模块：产品概览、用户旅程、饭局与供需、体验与留存、数据与定义。保留必要用户/饭局只读追溯与出席结果核实入口；不设计商家与场地、订单与财务、客服工单、内容与增长、社区与安全，也不增加商业活动、个人服务、会员或 AI 管理。数据与定义内增加统计账号分类，第一期不建独立账户信息页。

后台支持中英切换，中文默认。业务时间 Europe/London，GBP预算。以真实业务为指标目标，不以 Demo 中模拟注册/获准/支付/赴约作为业务成效。

### 1.1 当前交付与真实能力的区别

| 能力 | 本轮 Demo | 真实试点接入 |
|---|---|---|
| 分析页面、筛选、字典、下钻、汇总导出 | 已实现，纯本地计算 | 接入有权限的数据查询服务 |
| 事件与业务数据 | 确定性虚构 fixture，固定快照 | 用户端埋点 + 后端权威结果 + 出席确认 |
| 出席核实 | 会话内模拟修订并重算，刷新恢复 | 身份权限、原始来源、版本校验及审计 |
| 数据接收、身份衔接、重复/迟到处理 | 纯函数与样本测试，不是线上采集服务 | 服务端校验、去重、身份映射及快照重建 |
| 账号、认证、授权、定时刷新 | 未实现；无生产连接 | 内部登录、服务端权限与定时作业 |
| A/B 实验、自动因果解释 | 不建设 | 只有具备样本和明确问题后再设计 |

Demo 不采集评审者的行为、不调用第三方分析、不发送真实通知；数据性质在“数据与定义”、交付文档和导出元数据集中说明，常规页面不重复开发备注。真实用户数据不可进入公开仓库或静态 fixture。

## 2. 使用者与权限

- 产品分析者：访问脱敏聚合、必要的伪名记录、指标定义，导出聚合数据。
- 试点记录核实者：在上述范围外核实已结束饭局的有效参与者出席记录；必须填写依据，不删除或覆盖原始证据。
- 生产接口在服务端校验访问范围；页面显隐、语言切换和 Demo 状态选择都不是权限机制。
- 不常规展示姓名、联系方式、消息正文、申请留言、精确位置、单方互选意愿。事件只含业务关联ID和必要枚举属性。
- 暂不设计完整员工管理界面；生产接入复用内部身份体系。默认不开放原始用户数据下载。

### 3.4 出席核实

饭局计划结束后，由发起人记录参与者出席，参与者可自报。首期计划结束为开始后2小时，使用服务端scheduledEndAt；到开始时间不代表结束。仅针对发起人及开始前已确认且未提前退出的成员建立应确认记录；整场取消不建立应确认人次。

状态：`present / absent / unknown / conflict`。双方一致或只有一方有记录时使用已有记录并保留来源；双方冲突标为待核实；无记录为未知。自报不是独立核实的事实保证。

核实者进入饭局详情，选择有效参与者，确认出席/未出席并填写依据，追加核实结果和操作者/时间/版本。核实结果优先解释冲突，但原始发起人和本人记录仍保留。不得给未确认者、提前退出者、已取消或尚未开始的饭局核实出席。

未确认、提前退出、未开始或取消的场次在详情中显示出席“不适用”，不混作缺失证据。人工核实不冒充本人自报；缺少依据时聚焦对应字段。

Demo核实仅修改本次浏览器内存，所有相关指标立即重算；刷新恢复fixture。真实版本必须用服务端授权、乐观版本检查、幂等操作及审计，不以前端按钮为权威。

## 4. 指标字典 v2

[首期运营指标与采集契约](measurement-contract.zh-CN.md)逐项定义运营问题、原始数据入口、统计逻辑、清洗与接入验收，为本节研发细化规范。

通用：人数按userId去重、人次按(userId, mealId)去重、申请按applicationId去重、饭局按mealId去重、事件按eventId去重；零分母返回null并显示“—”。所有比率同时显示分子分母。观察窗口按连续14/30天（24小时/天）计算，报表归日归周采用伦敦时间，周一开周。首尾周可能不完整，禁止把部分周当成完整周做增长结论。

### 4.1 核心结果与质量护栏

| ID | 指标与公式 | 入组/来源 | 决策与边界 |
|---|---|---|---|
| weekly | 每周确认出席用户数：该周有有效出席的不同用户数，包括发起人 | 饭局开始周；参与事实+最新有效出席记录 | 衡量真实见面规模，同周多场只计一次；与覆盖率并看 |
| activation | 首次申请后14天内出席率：首次申请后14天内第一次实际出席的用户 / 首次申请后已完整观察14天的用户 | 全历史首次申请发生在所选期；真实申请+首次出席 | 不将重复申请错当首次；仅发起无申请者看发起路径；缺记录会低估 |
| retention | 首次出席后30天内再赴约率：首次出席后30天内再次参加不同饭局的用户 / 首次出席后已完整观察30天的用户 | 全历史首次出席发生在所选期；跨不同mealId | 近期队列单列观察中；不是App打开留存，也不是意愿 |
| coverage | 出席结果记录覆盖率：(明确出席+明确未出席)人次 / 已结束未取消饭局的应确认人次 | 饭局开始日；含发起人与有效确认成员 | 未知、冲突不计入分子；不把未知算失约 |
| cancellation | 饭局取消率：已取消场次 / 已到计划开始时间的已发布场次 | 计划开始日，取消场次仍在分母 | 分拆人数不足、发起人、订位、其他、未知；不混入个人退出 |

首次申请/首次出席的查找使用完整可用历史，不能先筛选日期再取“首次”。如只有迁移后的部分历史，返回historyCoverageStart并标记“可观测首次”，不宣称终身首次。

默认28天的首次出席队列不会有完整30天窗口，显示无成熟分母是正确结果。提供90天入口，并明确后续观测截止快照。

### 4.2 加入漏斗

浏览阶段展示发现请求的去重访问者、有效饭局曝光用户、详情用户。这是期内行为概览，用户可跨场浏览，**不是所有相邻行都可相除的严格嵌套漏斗**。

| 指标 | 定义与单位 | 解释 |
|---|---|---|
| 有效曝光 | 饭局卡片至少50%可见、连续1秒；同sessionId+mealId只保留首次曝光 | 客户端必须满足曝光规则；服务端去重重试 |
| 发现后7天申请率 | 至少一次成熟发现请求后7天内成功申请的去重用户 / 有至少一次成熟发现请求的去重用户 | 注册前后仅经明确身份衔接；无衔接匿名用户不猜测转化 |
| 有曝光但7天未申请 | 有成熟有效曝光但未在任一成熟曝光后7天内申请的用户 / 有成熟有效曝光用户 | 需要结合详情、供给与可选退出原因解释，不自动认定体验差 |
| 申请→获准→确认 | 所选期成功申请记录中，按同applicationId/mealId跟踪审核与席位结果到快照 | 用申请记录为单位；确认含需要预付后才确认的路径，不建设财务台 |
| 申请→出席 | 已结束至少24小时的关联场次申请记录中，有有效出席的申请 / 全部该类申请 | 未获准、取消、未出席均保留；出席缺失另展示 |
| 审核耗时 | 申请成功→首次有效审核，已处理样本的中位数与P90小时数 | 使用最近秩法；待处理数量、等待小时另列，避免只看已处理 |

### 4.3 发起、供需与功能

- 发起漏斗：按期内`create_started`的attemptId建队列，跟踪同一用户的`create_arranged`、`meal_published`至快照。重复事件不增加尝试数；跨期完成仍属于原尝试。
- 饭局结果：按计划开饭日统计已发布、收到申请、曾达最低人数、取消、有出席证据的实际场次。至少一人确认出席仅称“有出席证据”，不据此声称整场完整履约。
- 开始前招募达标率：计划开始前确认人数曾达minimum的场次 / 已到计划开始时间的已发布场次，取消仍留分母。人数上限与minimum分别保存，双人例子不等于真实试点已承诺双人上线。
- 无结果率：`discovery_results.resultCount=0`的有效请求 / 有效发现请求；请求失败另记error，不伪装零结果。另看受影响用户以及区域、日期、预算、语言、人数、来源。
- 功能诊断：地图、筛选、资料、创建、申请、群聊等使用人数；表单错误按步骤与字段归类；有明确尝试/成功事件的功能再计算完成/错误率。缺少适用分母的功能不虚构转化。
- 可选放弃/退出原因使用固定枚举和“其他/未填写”，不把未填写推断为某一原因；不采集敏感自由文本作分析属性。

### 4.4 反馈与留存解释

App饭后页新增整场私密体验评分1–5、是否愿再参加Fancy饭局、可选多项原因；本人出席与host名单报告作为出席入口。整场体验与针对某人的公评、私密互选相互独立，详见主PRD的P-11规则。

- 反馈覆盖：有效反馈人次/确认出席人次，同一用户同场保留最新有效反馈。
- 五级体验评价：显示1–5分布及样本数，不用均分描述所有参与者；反馈数据存在自选择偏差。
- 愿再参加：回答愿意的有效反馈/有效反馈，同时展示反馈覆盖；不等于实际重复赴约。
- 后续机会曝光：成熟首次出席用户中，在首次出席后30天内有效曝光另一场未来可申请饭局的比例。仅为看见机会的代理；没有曝光不证明没有可用供给。
- 后续机会与重复赴约可发生在不同区域、来源或语言的饭局；入组筛选不裁掉其后续结果。
- 安全和私密互选不因精简后台而改变用户端既有规则；分析者不查看单方意愿或聊天正文。

## 5. 事件与数据契约

### 5.1 公共事件信封

```ts
type AnalyticsEvent = {
  id: string;                 // 客户端生成后重试复用
  name: string; schemaVersion: number; appVersion: string;
  occurredAt: string;         // ISO UTC，客户端事件发生时间
  receivedAt: string;         // 服务端赋值，不信任客户端
  environment: 'production' | 'demo';
  sessionId: string;
  userId?: string; anonymousId?: string;
  mealId?: string; attemptId?: string;
  isTest?: boolean; isStaff?: boolean; isBot?: boolean; // 生产由可信服务标记
};
```

session默认30分钟无活动后更新；会话生成与过期在采集SDK实现，当前后台没有采集SDK。禁止用姓名、邮箱、IP、聊天文本或设备指纹代替userId。登录时仅建立授权会话内(anonymousId, sessionId)→userId映射，不猜测跨设备/家庭身份。

### 5.2 最小事件目录

| 事件 | 触发及专有字段 | 权威来源 |
|---|---|---|
| registration_completed | 真实账号创建完成；accountId去标识映射到userId | 服务端 |
| discovery_results | 请求成功返回；requestId、resultCount及实际筛选area/date/time/budget/size/language/source | 发现服务结果；客户端补展示属性 |
| meal_impression | 满足可见比例和时长；mealId、visibleRatio、durationMs | 客户端；不能将响应返回当曝光 |
| detail_view / profile_view | 页面实际呈现；mealId、入口，资料用去标识关联ID | 客户端 |
| filter_applied / map_opened | 筛选应用成功/切换地图；实际筛选值 | 客户端 |
| application_attempt | 用户确认申请；mealId、attemptId | 客户端 |
| application_succeeded / application_decided / seat_confirmed | 权威业务成功；applicationId、mealId、状态版本 | 服务端；点击不等于成功 |
| create_started / create_arranged | 创建尝试开始/安排校验完成；attemptId | 客户端 |
| meal_published / meal_cancelled | 发布成功/取消；mealId、attemptId、原因、版本 | 服务端 |
| form_error | 校验失败；attemptId、step、field、固定errorCode，不能发送输入值 | 客户端 |
| chat_opened | 有权限的群聊打开；mealId，不含正文 | 客户端 |
| attendance_reported / attendance_verified | 出席事实追加/核实；mealId、userId、来源、版本 | 服务端 |
| feedback_submitted | 有资格用户的反馈提交成功；mealId、score、again、reasons固定多选枚举（旧issue仅兼容） | 服务端 |

生产业务事实包括User、Meal、Application、AttendanceRecord、Feedback。申请保留成功、审核、确认、退出时间；饭局保留发布/开始/取消/最低人数、scheduledEndAt及开始前席位变更；出席保留来源、冲突、核实及版本；反馈同人同场去重。

不得把客户端自己传来的业务成功事件直接作为业务权威。客户端采集endpoint只允许交互事件，申请/席位等由业务服务通过可靠事件或查询供给。

### 5.3 清洗与快照

1. 校验必需字段与时间格式；缺字段隔离并返回原因，不参与指标。
2. 按eventId去重；排除demo、员工、测试与机器人。生产标记由可信服务决定，不能靠任意客户端字段绕过。
3. 分析同时满足发生及接收时间不晚于快照；迟到数据在后续快照按发生时间回补，不新增重复业务结果。
4. 出席/反馈按(userId,mealId)取快照前最新有效版本；相同时间以服务端版本/序列决定，保留原始记录。
5. 所有查询返回snapshotId、asOf、definitionVersion、historyCoverageStart、sourceStatus、quality。数据未接入返回缺失/未就绪，不回填模拟值。
6. 单次仪表板请求复用同一快照，不把不同更新时间的数相除。生产首期每小时更新一次，按实际延迟展示；后台展示时间不得伪装实时。

Demo固定快照为2026-10-18T12:00:00Z（伦敦13:00 BST），无定时作业。fixture中的production标记仅模拟生产筛选，不代表真实生产数据。

## 6. 目标接口与接入流程

接口为后续研发契约，**本轮没有建设这些HTTP服务**。Demo由纯函数与本地fixture呈现等价分析，代码不假装已经调用API。

| 接口 | 输入 | 输出/限制 |
|---|---|---|
| POST /v1/analytics/events | 合法客户端事件批次（≤100条），认证会话或有效匿名会话 | acceptedIds、duplicateIds、rejected；服务端赋receivedAt和流量分类 |
| GET /v1/admin/analytics/snapshot | start/end、area/source/language/size/budget/segment | 统一快照metadata及上述5模块聚合、分子分母与队列；用户粒度数据按权限另查 |
| GET /v1/admin/analytics/records | snapshotId、kind=meal/application/user/event、筛选、query、cursor、limit≤50 | 稳定排序记录及nextCursor；不能绕过数据范围 |
| GET /v1/admin/analytics/definitions | version、locale | 指标ID、单位、公式、窗口、来源、边界与支持决策 |
| GET /v1/admin/meals/:id/evidence | snapshotId | 必要参与、出席及业务时间线，不含聊天或支付凭据 |
| POST /v1/admin/meals/:id/attendance-verifications | userId、result、basis、expectedVersion、intentKey | 追加核实记录与审计，返回newVersion；409要求重新加载，不能静默覆盖 |

记录接口结果只在授权范围内可见；401/403不回敏感结果，400/422字段错误，409版本冲突，429退避，503来源不可用。后台真实接入需要取消过时请求，错误保留筛选但隐藏失效图表，重试使用相同参数；请求竞争不能覆盖新筛选结果。

接入顺序：身份/会话与业务事实→用户端最小事件→出席确认与反馈→服务端清洗及快照→后台查询适配→与手工样本逐项核对。先内部试点、再按权限开放，不把公开Demo URL当内部系统权限边界。

## 7. 产品迭代评审方法

每周按“数据质量→真实见面→加入与创建→供需分群→重复参与”复盘。每个判断必须包含样本/分母、对比范围、已知限制和一个可验证下一步。

| 观察 | 待验证解释 | 产品动作与结果验证 |
|---|---|---|
| 区域/日期无结果多 | 局部供给不足或筛选组合太窄 | 补特定供给/改无结果引导；比较申请与赴约，不能只看浏览 |
| 有曝光但详情少 | 卡片信息不足或场次不吸引 | 验证卡片信息；确认后续申请与体验不下降 |
| 详情多申请少 | 同桌/费用/安排不清，或申请成本高 | 修改信息与申请步骤，比较申请成功及真实赴约 |
| 申请后等待长 | 审核提醒、发起人负担或期限不清 | 改提醒/预期说明，比较等待、确认及退出 |
| 已确认但出席少 | 协调、改期或记录缺失 | 先补证据，再检查提醒/取消流程 |
| 首次正常、重复低 | 体验不足或后续机会不足 | 对照反馈覆盖和曝光机会，补供给或改善体验 |

不将相关性称因果、不以小样本排名、不拿行业或竞品自报阈值当本产品达标线。暂无可靠基线，先运行2–4周验证采集完整性，再确定改善目标；30天指标必须等窗口成熟。影响用户的界面迭代后记录版本与发布日期；本版不构建自动实验平台。

## 8. 验收与交付

| 编号 | 场景 | 验收 |
|---|---|---|
| AC-01 | 概览→字典→关闭 | 可查看完整公式、单位、分母、来源与窗口，Escape/关闭恢复焦点 |
| AC-02 | 区域/来源/语言/预算/人数/用户分群 | 所有适用指标使用同一筛选；场次不受用户分群的差异显式说明 |
| AC-03 | 加入、发起、申请下钻 | 同一业务ID关联，不跨场冒认成功；创建按同attemptId及用户跟踪跨期完成 |
| AC-04 | 28天→90天队列 | 30天未成熟不进分母，显示观察中；成熟结果与逐用户事实一致 |
| AC-05 | 缺失/冲突出席 | 与明确未出席分开；核实保留来源，拒绝无资格、未结束及取消场次 |
| AC-06 | 重复/测试/员工/机器人/迟到/缺字段 | 去重、排除、隔离和快照边界可重现；迟到不提前进入旧快照 |
| AC-07 | 反馈重复与零分母 | 同人同场不重计；无分母显示未知，不显示0% |
| AC-08 | 日期跨英国夏令时 | 归日归周准确，连续观察窗与本地日期分开处理 |
| AC-09 | 空数据/错误/恢复 | 不展示旧图表或伪造零值，保留筛选，重试有明确结果 |
| AC-10 | 中英/桌面/390px/键盘 | 翻译、导航、筛选、详情及反馈可用；表格滚动，页面无横向溢出 |
| AC-11 | 导出与隐私 | 聚合导出包含快照与筛选，不泄漏聊天/联系方式；Demo标明虚构 |
| AC-13 | 精简交互与动态检查 | 外部点击/Escape收起；隐藏条件可见；90天成熟状态不沿用28天提示；整组队列可追溯；普通页面无测试开关；详见审查记录 |
| AC-12 | 真实接入前检查 | 服务端身份权限、历史覆盖、权威业务结果、出席采集、共同快照均成立后才称真实后台 |

实现位于`admin/`。不修改已有手机端运行时；后续用户端埋点接入单独提交并遵循其运行时保护规则。每次实质变更增加相关测试、通过验证、创建对应commit、同步GitHub并核对SHA。本次仅同步后台相关修改，保留其他并行工作。
