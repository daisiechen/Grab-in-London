# Fancy 模块与需求版本拆分（2026-10-26）

## 当前指令与适用边界

用户否定继续按P1.1整包推进，要求先拆分模块与需求版本。本轮交付范围仅为拆分，不启动开发、业务QA、部署或外部服务调用。本方案取代前次复盘中“先继续完成P1.1消息扩展”的建议；本会话没有派发任务或调用工具中断其他会话，不能将本文件理解为所有worker已实际停机。

本文件为协调层需求分解方案，不代改原负责人持有的主PRD、补丁PRD、Demo、Figma或任务表。已有业务规则仍以主PRD§0、FR-13及已确认补丁增量为准；改变交付顺序不取消需求，也不追认任何未测项通过。D01—D19为本方案需求交付编号，不是产品发布号、Git tag或新的P1.1名称。

## 3. 排序与启动规则

先完成需求拆分签收与已有产物盘点，随后按D01—D19依赖推进；编号用于排清范围，不强制所有已实现模块从头重写。主要业务链为账号→发现/发起→申请→沟通→饭后→支持；后台按事件依赖接入；AI在普通编辑器稳定后进入；分享、提及、系统通知各自独立排期。

当前不再以“把P1.1做完”为worker目标。每次只激活一个需求版本作为主要交付目标；若有不影响其契约、文件和环境的独立工作，另由PJ明确排期，不能自动并发扩展。一个版本内遇阻塞不自动切换成新需求或改造平台。

模块内部每个worker只接一条用户任务和一个可验证结果，列基线、允许文件、依赖接口、需求/Figma引用、范围外事项和证据。环境/测试工具负责人独立于业务QA，现有开发、PRD/Demo唯一owner规则保留。

## 4. 共用依赖：只准备当前版本需要的部分

基础会话/权限、API契约与迁移/生成物、餐厅/身份/邮件/模型接入、运行环境与测试数据为共用能力，均指定单一负责人。它们不是新的大版本，也不作为“先重搭全项目平台”的理由。

每需求版测试前只预检其需要的精确构建、种子数据、账号角色、时间和故障注入；不相关的push/真实模型/后台全套环境不应阻塞例如资料页面验收。凡原验收要求真实服务的部分，依赖不齐记BLOCKED，不用mock关掉真实门槛。

验收划分为模块验证、跨模块合同验证、最终发布验证。支持删除等天然跨模块行为必须保留完整联合验证；模块拆分减少前置复杂度，不拆掉隐私/权限/并发断言。真实AI仍在原首期范围，推送仍在已批准补丁范围；若将任何需求移出产品发布版本，另需明确产品决定。

## 6. 每需求版的需求交付包

每版只交：一份范围明确的模块需求增量、适用的冻结Figma节点/共享组件规则、最小接口与跨模块依赖、短验收清单及测试前置、已有资产差异表。无需复制主PRD全文、重复全局异常说明或为每种组合新增画板。

模块需求版本与Figma版本分别登记并互相引用；没有设计变更不重绘，有关键交互缺口由原UX补齐。接口变更只升级对应契约，跨模块受影响方需确认。只有本版范围及验收闭合才称该需求版完成；“已有代码”“单测通过”“已发布”分别报告。

下一步应先盘点并形成D01的需求交付包，同时保留其余版本的范围清单；本轮不自动开始D01设计、实现或测试。发布组合和上线日期留到模块范围与证据对齐后确定。
