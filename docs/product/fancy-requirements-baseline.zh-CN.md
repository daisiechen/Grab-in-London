# Fancy 产品目标与模块需求基线

修订：r02｜日期：2026-10-26（Europe/London）｜作者职责：项目协调负责人｜状态：待用户审阅的需求组织方案。

## 1. 产品背景与预期价值

Fancy面向在伦敦生活、希望认识新朋友的成年人。用户可能已经愿意外出吃饭，但难以找到时间、预算和交流期待相近的同伴；组织者也需要把聚餐安排、人员审核和见面前沟通衔接起来。这是产品要解决的问题假设，尚不能当作已验证市场规模或增长效果。

产品希望用户能找到一场合适的饭局，了解参加条件，主动申请并获得明确答复，在见面前沟通，饭后记录体验，并在双方愿意时继续联系。品牌表达为“吃个饭，认识一下。 / Meet new people over a meal.”。产品不保证交友结果、成员合拍或餐厅有位。

真实首期由发起人在平台外订餐厅，参加者到店各自付款。平台展示预计人均预算及发起人的订位声明，不承担平台收款、退款、库存或代订位。移动Web和iOS保持业务规则一致；内部Web后台服务于产品分析与有限数据管理。

## 3. 谁使用Fancy、谁有权做什么

| 人与目的 | 可做的事 | 必须保持的边界 |
| --- | --- | --- |
| 访客想先了解 | 浏览发现、公开详情/主页/已发布公评，分享公开链接 | 不读邮箱、消息、申请留言、单方再约或私密记录 |
| 参加者想加入 | 登录及补资料后主动申请、撤回、在规则内退席，获准后沟通 | 不自动获准、不绕名额/截止，不因退席自动退群 |
| 发起人想组织 | 发布及在允许阶段编辑、审核、更新外订声明、开始前取消整场 | 首次批准锁关键安排；不能代替餐厅确认、不把成员自动搬去新场 |
| 同桌者想反馈或再联系 | 在资格/窗口内报告出席、评价、私评分或再约 | 单方意愿保密，互选才开放私聊；撤回/拉黑及时收回未来写权限 |
| 本人或举报者需要帮助 | 提交举报、查本人受理、重新认证申请删除 | 受理不称处理完成，公开参考编号不作为访问凭证 |
| 支持人员处理个案 | 按个案授权追加纠错、处理删除与举报 | 不默认开放所有消息、单方意愿或全表数据 |
| 分析者/数据管理员 | 分别读脱敏统计、维护测试/员工分类 | 分析后台不获得客服、财务或业务代办权限 |

## 4. 用户自然路径与完成结果

### U01 先看看，再决定是否参加

用户从欢迎页进入Discover，在地图或列表筛选合适的日期、区域、人数与预算；打开详情读懂地点、预计费用和参加状态，返回保留筛选。访客可以完成这段浏览，不先索取无关系统权限。对应M01/M02、D01/D02。

验收结果：同一筛选在地图与列表一致；空结果、查询失败和不可访问对象明确区分；公开内容不含私密字段。点击申请才进入身份/资料及M04流程，登录回流不替用户提交。

### U02 发起一顿饭，等待合适的人加入

发起人完成四步创建，主动确认餐厅、时间、人数、预算及外订声明，Review后发布。另一人主动申请，发起人审核，获准者直接确认并入群。对应M03/M04、D03/D04。

验收结果：不出现首期平台订金；Pending不占位；最后名额、精确截止、批准后安排锁与声明更新正确。失败保留原稿，未知结果查原意图，不重复发布或申请。

### U03 沟通见面，饭后选择是否继续联系

获准者从Inbox进入群聊，正常收发安排消息。饭局结束后记录出席、单场体验与对人的反馈；双方愿意再约才可私聊，任何一方能撤回或拉黑。对应M05/M06、D05—D07。

验收结果：退席、退群、解散不混同；只读历史只含授权区间；本人出席优先、未知不作缺席；公评、私评分、产品问卷和再约分别保存，不相互推断。失败/部分保存可辨认，第三人读不到私密意愿。

### U04 记录有误或需要离开平台

用户私密举报并获取受理回执，授权支持人员按个案处理逾期纠错。本人也能重新认证申请删除，受理先阻断未来业务权限，随后通过最小回执查询处理结果；无法查询时可未登录联系公开支持。对应M07、D08/D09。

验收结果：原报告与修订历史保留，纠错传播到资格及新快照；删除后的旧会话与导出不可继续使用，受理不假称完成。需要其他模块验证的结果单列联合断言，不能只测支持按钮。

### U05 内部团队读懂业务是否发生

分析者从五页后台选择查询、查看口径并下钻；数据管理员调整测试/员工分类，等待新统计就绪，再用相同有效快照导出聚合结果。对应M08、D10—D12。

验收结果：数据与手算/权威事实一致；缺失、观察中与零值不同；分类已保存不等于统计已就绪；问卷和单场评分分离；旧快照失效后不能继续读取旧导出。

### U06 获得帮助、邀请朋友和接收提醒

用户主动请求AI查找/解释或写草稿，转入原编辑器后自己提交；公开饭局可以分享，朋友自行申请；群成员可以明确提及别人或设置免打扰，系统通知在授权设备按规则投递。对应M09—M12、D13—D19。

验收结果：AI不自动代办、分享不免审核、提及不授新权限。应用内提醒和锁屏投递分别验证；真实供应方、外部App和设备证据不以模拟效果替代。新增帮助能力不能阻塞已独立可验的基础资料/浏览流程。

## 6. 设计、研发与测试的共同完成边界

设计先对应用户路径和验收，再选择页面/组件；复用已冻结稿，只补本版缺口。共享失败、焦点、返回、加载规则可用组件/状态表，不要求每页每异常重复新增画板。新增业务分支或强制字段必须有需求依据；没有依据先列候选，不进入当前工作包。

研发先对照既有代码列可继承、需改和未验证部分，固定一条路径的实现范围。服务端权限与跨模块规则保留统一权威，不能按界面模块复制席位、授权或统计逻辑。详细接口/技术选型由研发展开，需求包不把实现猜测写成用户要求。

QA先验环境与精确构建，再执行本版最小正常链和关键异常。环境/工具故障交给对应负责人，不用业务QA临场改数据库、预算或权限绕过；独立用例可继续，依赖故障的断言保留BLOCKED。产品缺陷、脚本故障、环境问题和需求歧义分别记录。已通过且仍适用的证据只复核变更影响，最终保留必要跨模块与发布验证。

文档完成、设计冻结、代码存在、模块测试通过、真实服务通过和发布分别报告。需求包静态验证只能检查目录/引用/覆盖，不证明用户体验、业务完成或worker一定不会偏离。
