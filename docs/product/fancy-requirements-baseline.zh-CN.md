## 1. 产品解决什么问题

Fancy面向在伦敦生活、希望通过聚餐认识新朋友的成年人。用户可能愿意外出吃饭，却难找到时间、预算和交流期待合适的同伴；愿意组织的人也需要把安排、人员审核与见面前沟通衔接起来。上述问题是产品假设，不是已经验证的市场或增长结论。

MVP希望让用户完成一条有明确结果的路径：找到合适饭局→了解条件→主动申请并获答复→见面前沟通→饭后反馈→双方愿意时继续联系。品牌表达为“吃个饭，认识一下。 / Meet new people over a meal.”，不保证交友结果、成员合拍或餐厅有位。

发起人在平台外订餐厅，参加者到店各自付款。平台只展示预计人均预算与发起人的订位声明，不提供平台支付、退款、餐厅库存或代订位。

## 2. 本版平台与产品范围

本节是完整MVP规划范围；首次对外可用能力取第5节的首发子集，未纳入首发的入口不提前展示。

| 产品端 | 本版范围 |
| --- | --- |
| iOS App | 账号资料、发现详情、发起安排、申请成员、聊天、饭后反馈/联系、举报删除、AI助手、iOS分享、提及免打扰与iOS系统通知 |
| 管理后台Web | 内部五页数据分析、口径、分类、快照、下钻与聚合导出；保持既定中英与后台响应式范围 |
| 移动Web前台 | 后续版本；本版不提供新移动Web页面、分享接收流程或Web Push |

后台作为Web产品仍在本版，不能与面向参加者的移动Web前台混同。本版功能范围不表示上述能力已经完成。

iOS公开分享中，未安装App的朋友如何查看邀请尚待确定；本版不承诺移动Web兜底。这个未决问题只影响完整邀请落地，不改变其他独立用户流程。

## 3. 产品使用者与权限

### 3.1 iOS App使用者

| 使用者 | 目标与可以进行的操作 | 产品权限边界 |
| --- | --- | --- |
| 访客 | 先浏览发现、公开饭局详情、公开主页与已发布评价 | 不能读邮箱、申请留言、群消息或私密记录；参加和创建时才进入登录/资料流程 |
| 申请人/参加者 | 主动申请、查看进度、撤回或在开饭前退席；获准后参与沟通 | 未获准不占席位也不获得群消息；退席与退群是不同动作 |
| 饭局发起人（host） | 发布安排、审核本场申请、更新外订声明、在允许阶段修改或取消 | 首位成员获准后锁定关键安排；不代餐厅确认，不自动把成员搬迁至新场 |
| 具有饭后资格的同桌者 | 报告出席、表达体验、评价他人并选择是否再约 | 单方意愿保密，双方愿意且资格有效才可私聊；撤回/拉黑收回未来发送权限 |
| 需要支持或离开的本人 | 私密举报、查询本人处理进度、重新认证申请删除 | 受理不代表处理完成，参考编号不是访问私密信息的凭证 |

同一个账号可在不同饭局拥有不同角色；“发起人”只对本人发起的那一场有效。

### 3.2 内部业务使用者

| 使用者 | 使用产品做什么 | 产品权限边界 |
| --- | --- | --- |
| 授权支持人员 | 依个案处理举报、逾期出席纠错与删除 | 不默认读取任意聊天、单方意愿或全量私密材料；不新增通用客服后台 |
| 产品分析者 | 通过数据后台读取脱敏统计并追溯必要事实 | 不因可读分析而取得纠错、删除或业务代办权限 |
| 数据管理员 | 维护正式/测试/员工统计分类，查看统计更新与审计结果 | 不改变饭局安排、出席来源规则或成员联系意愿 |

这些是产品中的业务使用者。开发者、项目协调者及测试人员的工程职责另见[项目管理方案](../delivery/project-management-plan.zh-CN.md)，不作为App账号角色或产品权限。

## 4. 产品模块按一次用户操作旅程划分

用户想办成的是“申请参加”“组织聚餐”“沟通赴约”或“处理一个问题”，不是“完成一个验证码界面”。因此完整注册、登录、必要资料、失败恢复和原入口返回必须嵌在所支持的旅程中；新用户不能在“下批再填资料”的边界被当作已完成参与流程。

| 旅程模块 | 用户目标与完成结果 |
| --- | --- |
| [J01 找到并申请一场合适的饭局](journey-modules.zh-CN.md#j01) | 申请有唯一可追踪结果，用户知道是否仍在待审；注册、登录和资料是途经步骤，不能只交付这些步骤就称本旅程完成。 |
| [J02 发起饭局并完成招募管理](journey-modules.zh-CN.md#j02) | 饭局真实发布且招募结果可管理：成员/名额/截止一致，取消或未成团有明确终态；不是只交创建表单。 |
| [J03 赴约前沟通安排或调整参与](journey-modules.zh-CN.md#j03) | 用户能完成一次实际协调或明确退出，并知道下一步去哪里；退席、退群、解散和饭局取消不会混成一个动作。 |
| [J04 饭后记录体验并决定是否继续联系](journey-modules.zh-CN.md#j04) | 饭后反馈各归其位；用户能在双方愿意时真正联系，或明确终止联系，而不是只停在互选成功提示。 |
| [J05 更新个人介绍或隐私选择](journey-modules.zh-CN.md#j05) | 本人看到自己确认的最新资料/选择及保存结果；他人公开主页只看到允许公开的部分。 |
| [J06 提交或更新一份产品意见](journey-modules.zh-CN.md#j06) | 本人可自愿提交并找回最新有效答案，未答不作No，未出席也不被挡住。 |
| [J07 举报问题并跟踪处理](journey-modules.zh-CN.md#j07) | 用户完成求助且能追踪，不把收件成功或一张回执当作问题已经处理。 |
| [J08 删除账号并确认处理结果](journey-modules.zh-CN.md#j08) | 账号删除从发起、受理、执行到结果恢复形成完整闭环，原会话/数据/导出不可继续使用；不只交一个删除按钮。 |
| [J09 支持人员处理一宗举报或出席纠错](journey-modules.zh-CN.md#j09) | 一宗事项有可核实处理结论与正确传播，而非只有CLI退出0或已读消息。 |
| [J10 查看约饭转化和供需并追溯原因](journey-modules.zh-CN.md#j10) | 内部用户能回答一个转化/供需问题并找到依据，不是逐页看到一些图表就算完成。 |
| [J11 调整统计分类并拿到可信导出](journey-modules.zh-CN.md#j11) | 从分类修改到新结果/导出闭合，既不显示旧统计为新结果，也不只交付保存按钮。 |
| [J12 分析饭后体验与后续赴约](journey-modules.zh-CN.md#j12) | 得到有观察窗口和分母依据的体验/回访判断，能追溯到权威事实。 |
| [J13 邀请朋友查看并申请饭局](journey-modules.zh-CN.md#j13) | 朋友能实际接到邀请、理解饭局并进入正常申请，而不是只弹出分享面板。 |
| [J14 发送普通群消息或提及并让对方收到提醒](journey-modules.zh-CN.md#j14) | 从普通群消息或提及发送到接收方实际有权看到提醒与消息闭合，不把事件入队或供应商接受当已送达。 |
| [J15 减少群消息打扰但保留重要提及](journey-modules.zh-CN.md#j15) | 设置改变实际提醒行为并能恢复，不是只有一个开关看起来改变。 |

[各旅程完整路径与边界](journey-modules.zh-CN.md)逐项说明使用者、触发、步骤、终点、异常和不做事项。第一份可体验的产品包应为J01：浏览/筛选/详情→必要时注册/登录→新用户补齐资料→回原饭局→主动申请→待审/撤回，已有用户不重复注册，访客可只浏览。账号入口仍不自动提交任何业务动作。

## 5. 首发与后续范围

首发iOS为J01—J08，以及确保举报/纠错可实际处理的支持运营J09；首发管理后台为J10/J11。后续增量为J12体验/留存、J13邀请、J14提及送达、J15免打扰，移动Web继续后置。不是按页面或接口数量定义版本，也不因重组取消旧业务要求。

AI融入选饭/申请、创建和群沟通的可选辅助路径，原只读、草稿转入、本人最终提交、数据许可及预算规则不变。完整首发仍需要原真实身份/地图/邮件/iOS/隐私/恢复与AI模型数据成本等证据；尚未宣称可上线或保证Apple审核通过。

## 6. 共同业务规则与不做事项

- 伦敦、18+、iOS英文、GBP预算、Europe/London时间；后台保持既定中英与响应式范围。2≤minimum≤capacity≤6，人数含host。
- 平台只展示预计预算与host外订声明；到店各自付款，不代订、不收平台订金。Pending不占位，批准直接确认，截止及关键安排锁按原规则。
- 退席、退群、解散、取消是不同动作；历史读取和未来发送权限分别判断。单方再约保密，互选才开私聊，撤回/拉黑不自动复活。
- 出席本人优先、host补缺、未知不算缺席；公评、私评分、再约及独立产品问卷分别保存，7天自助窗口与逾期支持纠错不混淆。
- AI不自动申请/发布/发送，不读群私聊或私密反馈；注册/登录与助手成功不等于业务已经完成。
- 删除从本人发起到实际处理/回执恢复完整闭合，同步屏障成功前不能202，后续供应商/物理清理不冒称已完成。
- 不做移动Web业务前台/Web Push、Android、支付退款/库存、通用客服/财务/商家平台、联系人采集或邀请奖励。
