# Fancy MVP 补丁版本 PRD

文档版本：0.2｜日期：2026-10-22｜状态：需求梳理中，未达到开发准入

## 1. 背景与目标

用户反馈：MVP 开发后发现前端实现与 Demo 存在出入，已引入 UX 设计师，并安排其补充 MVP 的 Figma 原型。具体差异尚未逐项核证；本文件不据此宣称当前 MVP 开发或测试通过。

本版目标是明确下一版的体验修正及必要需求，通过需求、Figma、对应版本 Demo 与验收项之间的映射指导前端实现，减少开发过程中的交互猜测。

## 2. 版本边界与基线

- 当前 MVP 继续按[主 PRD](PRD.zh-CN.md)、当前研发与测试基线执行；本文件不修改其范围、验收预期或缺陷关闭标准。
- 本补丁版为独立的下一版增量 PRD，不复制主 PRD 全文。未明确变更的业务规则引用已锁定的 MVP 基线；未来主 PRD 变动不自动纳入本版，须登记后核对。
- 创建时仓库 HEAD：`92c5e0d77fa546a3e6759b45ceaf0c113fe5bc78`；主 PRD 版本为 0.8 / AI 增补 0.3。该提交仅为文档起点，不代表 MVP 已验收或最终发布版本。
- 主 PRD Git blob：`5ae37b576369ac98789a9f54e5a75f750b09381a`。正式开发前记录 MVP 最终交接提交、补丁需求提交及设计版本。
- 本会话负责本补丁 PRD、UX 需求问答及需求决策整理；当前主 PRD、Demo、实现与 QA 仍由既有负责人维护。
- 当前 MVP 对既有需求的实现偏差继续由原开发/测试流程判定和处理；不通过补丁设计追认偏差或消除未关闭缺陷。改变需求或交互的决定进入本补丁范围。

## 3. 需求与设计的权威关系

| 产物 | 职责与约束 |
| --- | --- |
| 当前 MVP 主 PRD / 测试基线 | 当前版本业务规则与验收依据；本轮不修改 |
| 本补丁 PRD | 下一版已确认的需求差异、规则和验收依据；待确认建议不构成开发承诺 |
| UX Figma 原型 | 指导对应版本的信息架构、交互、布局、组件与状态；需记录文件、页面/节点、版本和对应需求 ID |
| 对应版本 Demo（必要时） | 验证交互或解释难以表达的路径；模拟数据和服务须标明，不作为真实接入证据 |
| 实现与验收证据 | 证明指定版本、平台和场景的实际行为，不能由设计稿或 Demo 替代 |

Figma 与需求冲突时先在本会话核对规则及证据，记录结论后更新对应版本产物。不能静默使用设计稿覆盖业务规则，也不能让前端自行裁定需求歧义。

### 3.1 Demo 版本隔离

用户已确认：必要的 Demo 改动必须使用补丁对应版本，不影响正在开发和测试中的 MVP 版本。

- 只有具体问题确需交互验证时才创建补丁 Demo；本轮未创建或修改 Demo。
- 开始前明确唯一文件负责人，记录源 Demo 的提交、补丁 Demo 的独立分支/工作区或目录、运行入口和依赖。不得复用并覆盖当前 MVP Demo 的可变入口。
- 补丁 Demo 的源码、共享组件改动、配置、构建输出及本地服务均须隔离，不能通过共享文件或端口切换改变当前开发/QA看到的版本。
- 补丁 Figma 也需明确独立页面或版本及对应节点，保留当前 MVP 被引用的设计基线；不得把新增稿默认为当前 MVP 验收依据。
- 补丁 Demo 与当前 MVP 的交接、合并和发布另按对应版本执行；仅制作原型不启动当前版本迁移。

## 4. UX 需求问答与决策

UX 设计师的问题统一在本会话答复并写回本文件。优先依据已确认业务规则；清晰的既有规则可直接解释，新增业务规则、范围变更或取舍尚无依据时保留待用户确认状态。原始聊天及个人信息不写入公开仓库。

每条问题记录：问题 ID、页面/场景与角色、问题及依据、答复、状态、适用版本、关联需求、Figma 节点及验收影响。状态区分「既有规则澄清」「建议/待确认」「已确认变更」「已关闭」。

已从原会话读取本轮问题与改动，归集见§9；后续统一在本会话答复。原会话转述的既有决定保留来源，不将其自动认定为本补丁新增需求。

## 5. 补丁需求清单

当前已确认的是协作方式与版本隔离，尚无已确认功能或交互改动。收到问题后使用 `PATCH-001` 起连续编号，每项完整描述：

- 用户目标、问题证据及当前行为与期望行为。
- 角色、入口、前置条件、业务规则及输入校验。
- 正常路径、状态反馈、返回/取消、草稿、异常及恢复。
- 涉及的权限、数据、通知、跨端及历史兼容影响；不涉及则明确说明。
- 优先级、确认状态、Figma 文件/节点/版本、补丁 Demo 路径及版本（如需）。
- 可观察的验收条件、回归范围与负责人。

现阶段不新增支付、订位、AI 自动代办等能力，也不默认重做导航或全站视觉；任何新增范围均须先形成具体需求决定。

## 6. 设计与开发准入

1. 收齐补充的 Figma 链接、适用平台和版本，以及 UX 设计师问题清单；逐项对照 MVP 需求与实际差异，区分实现缺陷、规则澄清及下一版变更。
2. 更新本文件的有效需求正文和问答结论；记录用户确认的范围及剩余未决项。
3. 对纳入补丁的路径补齐正常、加载、空、失败、权限与状态变化、返回/取消等适用设计；必要时使用隔离的补丁 Demo 验证。
4. 锁定本 PRD 提交、Figma 版本/节点与 Demo 提交；由研发核对可实现性和依赖，阻塞问题关闭后再进入补丁开发。
5. 按需求 ID 验收前端对 Figma 的交互与视觉还原，并回归受影响业务及 Web/iOS 路径；真实服务能力另需真实环境证据。

以上为补丁开发准入流程，不暂停或改变当前 MVP 的开发与测试。
