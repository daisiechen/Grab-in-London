# Fancy MVP 补丁版本 PRD

文档版本：0.5｜日期：2026-10-22｜状态：需求梳理中，未达到开发准入

## 1. 背景与目标

用户反馈：MVP 开发后发现前端实现与 Demo 存在出入，已引入 UX 设计师，并安排其补充 MVP 的 Figma 原型。具体差异尚未逐项核证；本文件不据此宣称当前 MVP 开发或测试通过。

本版目标是明确下一版的体验修正及必要需求，通过需求、Figma、对应版本 Demo 与验收项之间的映射指导前端实现，减少开发过程中的交互猜测。

## 2. 版本边界与基线

- 当前 MVP 继续按[主 PRD](PRD.zh-CN.md)、当前研发与测试基线执行；本文件不修改其范围、验收预期或缺陷关闭标准。
- 本补丁版为独立的下一版增量 PRD，不复制主 PRD 全文。未明确变更的业务规则引用已锁定的 MVP 基线；未来主 PRD 变动不自动纳入本版，须登记后核对。
- 创建时仓库 HEAD：`92c5e0d77fa546a3e6759b45ceaf0c113fe5bc78`；主 PRD 版本为 0.8 / AI 增补 0.3。该提交仅为文档起点，不代表 MVP 已验收或最终发布版本。
- 主 PRD Git blob：`5ae37b576369ac98789a9f54e5a75f750b09381a`。正式开发前记录 MVP 最终交接提交、补丁需求提交及设计版本。
- 本会话负责本补丁 PRD、UX 需求问答及需求决策整理；当前主 PRD、Demo、实现与 QA 仍由既有负责人维护。
- 当前 MVP 对既有需求的实现偏差继续由原开发/测试流程判定和处理；不通过补丁设计追认偏差或消除未关闭缺陷。改变需求或交互的决定进入本补丁范围。

### 3.1 Demo 版本隔离

用户已确认：必要的 Demo 改动必须使用补丁对应版本，不影响正在开发和测试中的 MVP 版本。

- 只有具体问题确需交互验证时才创建补丁 Demo；本轮未创建或修改 Demo。
- 开始前明确唯一文件负责人，记录源 Demo 的提交、补丁 Demo 的独立分支/工作区或目录、运行入口和依赖。不得复用并覆盖当前 MVP Demo 的可变入口。
- 补丁 Demo 的源码、共享组件改动、配置、构建输出及本地服务均须隔离，不能通过共享文件或端口切换改变当前开发/QA看到的版本。
- 补丁 Figma 也需明确独立页面或版本及对应节点，保留当前 MVP 被引用的设计基线；不得把新增稿默认为当前 MVP 验收依据。
- 补丁 Demo 与当前 MVP 的交接、合并和发布另按对应版本执行；仅制作原型不启动当前版本迁移。

- Google Places/照片、认证/邮件、真实AI价格与预算闸、支持/删除等外部能力按既有准入条件呈现；设计可表达加载、失败、权限拒绝和未启用，不声称真实接入已通过。
- 后台Loading/401/403/导出失败需在现有页面表达目标状态，不能冒充Demo已实现认证/API；coverage按本人优先、host补缺，来源不一致可形成明确结果并计分子，unknown不计分子。AC-006需覆盖该口径，无新增冲突核实队列。

- 不增加Android客户端、私聊@、支付退款、平台代订位、客服/员工账户管理模块。

### 5.3 PATCH-004 个人反馈保存与部分结果

依据主PRD§0.5独立对象与`packages/contracts/src/operations/social.ts`现行`reviewPerson`（正文1–500）及`selectReconnect`（布尔选择、独立版本）契约，补丁保留单个`Save feedback`按钮，不新增跨接口原子保存功能。

- 公评可选；首次空正文且未选再约、没有有效改变时允许点击，但不创建空review或虚构“已完成反馈”记录，提示`No changes to save`。空公评为跳过；已有公评清空时不调用空值覆盖或静默删除，保留输入并提示当前不能以空值覆盖既有评价。由已选再约改为未选属于明确变更，按原`selectReconnect(false)`语义保存，不当成无变化。
- 公评正文非空时去首尾空白并按1–500校验；资格、7天窗口及目标均按主PRD。公评和再约分别保存；成功项保留，失败项保留原文/选择及逐项错误，显示准确的全部成功、部分成功或失败结果，不自动回滚成功项。
- 部分结果可表述`Public reference saved`及`Reconnect choice couldn't be saved`，不假称全部成功。重试仅处理失败项；超时结果未知先核对权威状态，幂等重试不制造重复。409须加载权威版本并保留本地草稿供核对，不静默覆盖。
- 保存评价不等于公开发布，发布仍按双方提交或7天规则；再约仅展示服务端允许的本人/互选结果，不推断或泄露对方未互选选择。

AC-004a：空白无变更不发空review/不制造反馈记录；取消已有再约能正确提交false；既有公评不能被空白静默删除。AC-004b：两端点分别成功/失败/超时/409的组合有逐项真实回执、草稿保留及仅失败项重试，成功评价未到发布条件时不标published。

补充执行顺序（F01—F05）：

- 仅保存相对最近权威快照确有改变的项目。若当前连接已OPEN而本次取消再约会撤销双方同意，先沿用原撤回联系确认；确认取消则本次整次Save不提交任何项，公评草稿仍保留，不能先写公评再询问是否撤销。确认后沿用原revoke语义，不以普通false写绕过确认。
- 前置校验/确认完成后，串行先公评后再约；无公评改变则跳过。第一项确定失败、409或结果未知均暂停后续项，保留待处理选择；已成功项不回滚。失败项重试成功后才继续其后待处理项，不重复写已成功项。
- 超时/断网标记`Status unknown`，通过权威查询或同幂等请求核清再继续；409显式显示冲突并保留草稿供重新核对。不可将本次从未执行的后续项标“保存失败”，应标`Not saved yet`。
- 保存中绑定mealId+subjectId+账号；切换对象/离开/账号变化时，迟到结果不写入新对象界面，不自动对新对象提交。未决结果返回原对象后先查状态。窗口到期或资格改变后逐项重验，拒绝的项保留可解释反馈，不用之前成功项推断后续仍有资格。

AC-004c：OPEN连接取消先确认，取消确认时两项均无写入；公评成功、再约失败有部分结果，首项失败/未知时再约仍未执行；重试、切对象及窗口过期不会串写或重复写。

## 11. PATCH-007 Meal详情分享邀请

用户2026-10-22明确新增：从Meal详情分享到其他App，邀请朋友参加。适用iOS和移动Web；本节是补丁增量，不回填当前MVP。

### 11.1 入口、内容与接收路径

- 对可公开浏览的已发布Meal，在详情标题区提供`Share`（可访问名称`Share meal`）；访客、host及其他浏览者均可分享，不要求先申请。未发布草稿不分享。
- 分享内容为公开标题、伦敦当地日期时间（必要时BST/GMT）、餐厅/区域和稳定HTTPS详情链接；文案如“Join me for [title] on [date/time] — view details and apply: [link]”。不含申请留言、聊天、邮箱、私密资料或登录token。链接不是免审核邀请券、不占位、不自动批准。
- 朋友打开同一mealId详情，可先浏览；申请时沿用登录/资料门槛，完成后回到同一场次并保留申请草稿，仍需主动提交及host审核。未装App可用移动Web；已装iOS可在平台允许时通过Universal Link进入详情，不能强制安装才能浏览。
- 满员、已截止、已取消、已开始/结束仍可复制或分享事实详情，使用“View meal”而非“Join me”邀请文案并展示不可申请原因；删除/不存在/不可见链接展示不可用状态，不泄露原内容。打开时以服务端最新状态为准，外部聊天中的旧预览不可承诺实时更新。

## 12. PATCH-008 群聊提及、提醒与免打扰

用户2026-10-22明确新增：群聊可@具体用户和@所有人，被@者弹出提醒，并可屏蔽群消息。本节将“屏蔽群消息”定义为免打扰：消息仍接收、保留未读及可查看，不等同退群、拉黑或禁止发言。用户于2026-10-22明确确认：仅发起人可@所有人；开启免打扰后，@本人和@所有人仍提醒。以下权限及提醒矩阵据此执行，设计与实现仍需验收。

### 12.1 提及与权限

- 有当前写权限的群成员可输入`@`打开成员选择，也可搜索名字；以稳定userId绑定提及实体，显示同名成员的头像/区分信息。选择后形成可删除的提及标记，单独手打“@名字”或粘贴文字不自动触发提醒；输入文字与选择实体须可访问。
- 仅host可选`@Everyone`（@所有人），普通成员不可操作，服务端同样拒绝越权；可@当前群成员，不因其退席而排除仍在群中的成员。主动退群者、从未入群者不在候选/接收人中。host也必须具有当前群写权限。
- 发送时按当前群身份/权限核验并确定去重接收人，排除发送者；@所有人加单独@同一人只生成一份提醒。选择后有人退群则不提醒该人，其余合法提及与消息可正常发送；失效标记降为普通文字并向发送者说明。发送者失去写权限则整条发送失败，保留原稿。
- 提及不授予新权限、不邀请入群、不绕过授权历史区间。解散/只读群不能发送；重入成员不收到退群期间的历史提及提醒。失败/重试按同一messageId去重，不产生重复通知。

### 12.2 免打扰与提醒矩阵

群设置提供按“本人账号+群”持久保存并跨端一致的`Mute group notifications`，默认关闭；保存中、防重复操作、失败恢复原值并保留错误提示。不影响该群其他用户，也不影响业务通知（审批、整场取消等既有通知）。

| 场景 | 未免打扰 | 已免打扰 |
| --- | --- | --- |
| 普通群消息，本人在其他页面 | 可用应用内横幅；后台系统提醒按授权/能力投递 | 无弹出/声音，保留群未读 |
| @本人 / host @所有人，本人在其他页面 | 应用内横幅及提及标识；后台系统提醒按授权/能力投递 | 仍提醒，设置旁明确“Mentions still notify you” |
| 正在阅读该群且消息已可见 | 直接展示消息/提及高亮，不重复弹横幅或声音 | 同左 |
| 已退群、无读取权限或群已解散后新发事件 | 不生成新的消息提醒 | 同左 |

- 应用内横幅可关闭、可点击定位授权消息，不遮挡输入/强制跳转；用户处于该群但滚动查看旧消息时，用新消息/提及提示定位，不擅自滚动。

| Q5 设置并发与时序 | 保存以服务端返回为准；普通失败无并发迹象时恢复最近确认值，409冲突则刷新并展示服务端最新值，提示“Settings changed on another device. Latest settings loaded.”，不得用旧本地值覆盖另一端成功保存。消息接收人按发送事务确定，实际push/横幅显示前使用最新已知权威mute决定普通消息是否提醒；提及仍为例外。已交给系统供应商的提醒无法保证撤回 | 保存中、防连点、成功、普通失败、409刷新成功/失败及重试；权限变化不得伪装保存成功 |
| Q6 补丁契约边界 | 新增mentions、群通知设置与推送是PATCH008版本化增量，需新请求/DTO/迁移、站内/outbox及设备订阅/投递契约；旧消息/旧客户端纯文本兼容，通知去重不能只依赖单设备。沿用当前MVP无群推送的契约与QA基线，不回写为原MVP已支持；实施前由独立补丁开发会话补齐方案 | 外部授权/订阅/不支持/失败状态属设计依赖；画布覆盖不关闭真实接入门槛 |

免打扰影响应用内横幅、声音及后台普通群消息push，不隐藏消息或群未读；@本人和@所有人仍按授权与平台能力提醒。若用户刚在另一端设置mute而本机尚未获知，短暂旧状态提醒存在竞态；服务端投递使用最新设置，客户端应刷新设置，不承诺已发生的弹窗可撤回。通知读取与聊天读取是两种独立状态。

补充验收：

- AC-008i：普通消息、个人提及、全员提及使用正确通用文案，系统payload不包含私密正文；普通消息不产生逐条站内通知，提及只产生一条去重记录。
- AC-008j：设备A当前可见消息不弹本机横幅；A滚动旧消息有定位提示，设备B可按授权收到push，不以跨端同时绝对无重复为验收要求。
- AC-008k：发送后队列暂停，分别执行标已读、退群、解散、mute，再恢复worker，逐项核对投递抑制；消息创建满1小时未交给供应商的push不再发送，授权历史与站内提及仍保留。
- AC-008l：两端同时保存设置触发409，刷新权威值且不覆盖另一端；刷新失败显示未同步与重试，不能用旧值标保存成功。
- AC-008m：同一消息/提及、worker重放、多设备订阅分别有稳定事件与delivery标识；失效订阅、退出账号/账号切换不将前账号通知投给后账号。旧客户端纯文本消息不触发伪提及。

### 12.5 退群后的群设置与成员资料边界

主动退群确认成功后留在Group settings，显示`Left group`及只读说明；隐藏整个成员名单、当前人数、成员搜索和@候选。不新增“离群时历史成员名单快照”能力，不读取实时名册填充旧页面。退群不改变meal participation，不自动跳转聊天归档。

保留返回本人既有授权历史聊天的入口；历史消息中的既有发送者显示按原授权规则保留，不意味着获准查询当前成员。重新申请并获准入群后，才按新授权恢复当前名单；读取消息仍只覆盖各次授权区间，不补读退群空档。

AC-008n：退群成功后停留只读设置，成员名册/人数/搜索/@候选均不可见且不能通过对应接口获取实时名册；历史入口可读本人授权消息。原席位/饭局状态不因退群而改变，重入后分别核对名单恢复及历史区间限制。
