# Grab in London 产品需求文档（PRD）

版本：0.1｜日期：2026-10-16｜语言：中文｜阶段：高保真可交互 Demo

> 本文描述目标产品及 Demo 交互规格。已确认需求来自本项目讨论；补充参数标记为「Demo 默认」，用于形成可评审体验，不等于上线业务承诺。品牌 Grab 为工作名称，Slogan 已由用户确认。本轮不开发真实后端、不产生真实订位或扣款。

## 1. 需求背景与产品定位

### 1.1 背景与问题
伦敦的国际居民、新移居者及忙碌职场人士可能缺少能同时协调时间、预算与餐厅偏好的同伴。传统聊天需要反复商量，陌生人社交又存在目的不清、背景不了解、怕尴尬、失约和费用不透明等阻力。餐厅预约进一步要求提前确认人数与时间。以上是讨论形成的问题假设，尚未经过访谈或市场规模验证。

### 1.2 产品定位
将本来就要吃的一顿饭，变成认识新朋友的机会。面向在伦敦生活的成年人，以吃饭为场景建立日常社交连接；networking 与 dating 是可能的附加结果，不是默认目的。首发城市伦敦，面向不同国籍与文化背景；全球用户不意味着首轮同时运营全球城市。

已确认 Slogan：**一起吃顿饭，认识新朋友。 / Meet new people over a meal.**

核心价值：帮助用户找到合适的一顿饭、在见面前形成合理预期、低成本完成协调，并让舒服的一次见面有机会延续。

## 2. 产品设计目标与原则

| 编号 | 目标 | Demo 验收方式 |
| --- | --- | --- |
| G-01 | 轻松发现时间、地点、预算合适的饭局 | 地图/列表共享筛选，点击地点可选场次 |
| G-02 | 见面前了解同桌的人与饭局目的 | 详情可查看参与者主页、语言、氛围、费用 |
| G-03 | 明确加入、付款、成团、订位分别处于什么状态 | 审核、付款、预约状态分别展示，无相互冒充 |
| G-04 | 完成从发现到饭后联系的完整体验 | 加入者与发起者故事可端到端操作 |
| G-05 | 降低社交压力并尊重边界 | 无任意陌生人私信；再次联系需双方意愿 |
| G-06 | 为后续研发提供可追踪规格 | 功能、输入输出、异常、接口与验收编号对应 |

原则：先展示值得参加的机会，再要求完善资料；优先加入、保留显著发起入口；默认强调 3–6 人小饭局；background 帮助找话题，不做履历排名；私密信息最小化展示；模拟与真实服务明确区分；保留用户返回、取消、失败恢复路径；英文界面与英镑金额，伦敦本地时间展示。

上线后建议观察的指标（尚无数值目标）：发现→详情→申请→获准→确认席位→实际出席转化；订位成功率、取消/失约率；饭后愿意再约比例与重复赴约率；举报处理时效。浏览量或停留时长不单独代表成功。

## 3. 用户分析、角色与权限

### 3.1 用户画像与任务
| 用户类型 | 处境/动机 | 主要阻力 | 成功结果 |
| --- | --- | --- | --- |
| 新到伦敦者 | 想建立本地生活圈 | 没有朋友带入、不了解对象 | 参加第一场舒服的饭局 |
| 忙碌居民 | 朋友与自己空闲时间不同 | 反复协调成本高 | 在合适时段约成一顿饭 |
| 拓圈者 | 日常接触背景固定 | networking 压力、目的不明 | 认识不同背景的人 |
| 餐厅探索者 | 有明确想吃的餐厅 | 缺同伴、难确认人数订位 | 找到同行者并吃到想吃的餐厅 |
| 回访用户 | 想再见合拍的同伴 | 无自然再次邀约入口 | 双方愿意后持续联系、再次同桌 |

发起者与加入者是同一账号在不同饭局中的角色，不是两个账号类型。

## 4. 用户路径与信息架构

### 4.1 加入者路径
Discover → 列表/地图与筛选 → Meal detail → Participant profile（返回保持饭局）→ Apply → 缺资料则 Profile edit → 返回申请草稿 → Pending → Approved / Declined → 若需预付则 Checkout → Payment pending / Failed / Paid → Seat confirmed → Booking pending / Confirmed → Meal chat → Completed → Feedback → Mutual reconnect。

无预付饭局获准后直接确认席位。审核通过不等于付款成功；付款成功不等于餐厅已确认。饭局满员、已取消或已开始时不接受申请。

### 4.2 发起者路径
底部 Create meal → 选择餐厅 → 选择预约模式与时段 → 填写饭局说明、人数、语言与费用 → 校验与预览 → Publish → Host detail → Applications → 查看申请者 → Approve / Decline → 查看名额与付款情况 → 管理预约 → 群聊协调 → 完成/取消。

### 4.3 回访与再次联系
Meals 的历史饭局 → 参与者主页 → 私密选择愿意再次同桌 → 互选后 Connections/Inbox 开放私聊 → 再次邀请。可发现已关注同伴的公开饭局；不能据此泄露未公开行程。后者是目标设计扩展，本 Demo 不必完整实现关注网络。

## 6. 功能需求与详细交互

### FR-11 品牌开屏、登录注册与首次主页（P-15）

**产品目的**：让首次到访者先理解“在伦敦一起吃饭、认识新朋友”，再按参与意愿完成账号与个人介绍。品牌表达独立于参考：保留“品牌→账号→个人资料”的通用节奏，不复刻参考品牌的Logo、紫黑网格、手写字、渐变按钮或逐像素页面。

**品牌规范**：字标为紧凑粗体小写grab / in London，森林绿#123f35，品牌开屏柑橘绿#d7ee79，入口奶油白#f5f2e8，朱橙#e96943点缀。原创生成的俯视餐桌插画作为欢迎主视觉。主Slogan维持“一起吃顿饭，认识新朋友。 / Meet new people over a meal.”；There’s room for you here. 是欢迎页情绪标题，不替代Slogan。品牌名沿用项目工作名，不表示完成商标审查。

**权限与隐私**：游客可看地图/筛选、饭局详情和公开示例主页。申请、发起、本人资料、Meals、Inbox及支付需登录；Demo客户端门禁用于演示，真实后端必须独立鉴权。邮箱与验证码不写仓库、不存持久化、不展示于公开主页。新用户资料是公开介绍，页面明确提示仅填写愿意公开的内容。示例隐私/社区说明可展开，明确不是生产法律文书；未来上线需完整条款、隐私说明、账号删除与申诉机制。

**输入输出**：目标认证请求使用邮箱/供应商授权与安全nonce，输出session、accountState、profileCompleteness、allowedActions；公开资料独立于私有身份。Demo仅本地状态，没有真实账户唯一性、OAuth授权、token、邮件、服务端频控、设备会话或数据删除功能。

**前后端职责**：fe-entry负责页面、输入校验、键盘、加载/取消/回流；identity后端负责OTP签发/哈希与核验、尝试次数/频率限制、一次性消费、会话生命周期、供应商token校验和同邮箱账号合并确认；profile保存公开字段并过滤隐私。供应商取消/网络失败应返回可重试入口；账号冲突不得自动绑定，封禁/已删除账户不得继续；这些是目标后端要求，本轮不接入。

**验收**：AC-A01游客浏览无阻；AC-A02游客点Create后完成模拟注册返回Create；AC-A03非法邮箱、错误/过期验证码阻止继续且可恢复；AC-A04供应商取消保留入口；AC-A05名字/介绍/社区确认缺失阻止完成；AC-A06成功后头像与主页一致；AC-A07已有用户不重复填资料；AC-A08刷新不会假称仍有真实登录会话。

### FR-01 发现饭局（P-01）
- 输入：日期/时间、区域、预算、人数、语言、氛围、饮食偏好；列表/地图模式。
- 输出：符合条件的公开饭局、区域聚合标记、剩余席位、费用类型及详情入口。地图数字表示该区域符合当前筛选条件的饭局数量；饭局人数只在卡片中以 Table for N / confirmed 表达，不能混用。
- 操作：默认地图；切换列表保留筛选与选中饭局；点击区域标记更新底部卡片，可前后翻页查看该区域饭局；小横线及 View all 入口展开区域全部饭局。卡片整体可点进入 P-02，头像独立进入 P-03；移除重复 View meal/箭头按钮；返回恢复筛选、区域和当前卡片。
- Demo 默认：固定中央伦敦示意地图，不申请用户定位，不展示伪造实时导航；提供五个固定饭局，包含双人示例。日期 2026-10-23 与 2026-10-24。
- 校验/边界：条件交集无结果→说明并提供 Clear filters；地图与列表结果一致；已取消饭局不参与推荐；取消席位后计数更新；餐厅详情不代表已订位。

#### FR-01a 快捷筛选与完整筛选（2026-10-16 修订）
- 首页优先级：日期、Table size；预算收进 More filters。日期按钮只打开日期选择；人数按钮只打开人数选择，不直接打开全量表单。
- 日期：月视图，前后月份，已过日期不可选；使用英国英文、伦敦日期，示例时钟为2026-10-16。可选无饭局的未来日期，应用后显示空态；有饭局的日期标记小点。日期选项使用原生单选语义，可用方向键切换、空格选择；关闭弹层不提交。
- 人数：Any size / 3–6 people / 2 / 3 / 4 / 5 / 6；人数含发起人，不是剩余名额。选项使用单选标签，不使用系统 select 下拉。
- 全量筛选：日期、人数、时段、区域、预算、语言、氛围、菜系、饮食选项及关键词。日期面板可展开，其余使用成组单选标签。仅提供有示例数据定义的选项，不宣称适合所有饮食限制。

**依赖更新**：餐厅、日期或人数变化后重新计算时段；已有时间仍适用则保留，否则清空，要求重选。日期变化始终重选时段。安排变动清空外部预约声明与最终核对，避免沿用旧承诺。餐厅变化重设建议预算；其他草稿字段保留。费用、介绍等修改后清空最终核对。

**编辑边界**：草稿仅本轮内存保存；发布后关键时间/地点/价格/条款修改需参与者重新确认是目标需求，本轮不覆盖已支付约定；演示可取消并重新创建。真实版本补充外订凭证、餐厅搜索与供应商库存、发起人结算、跨时区存储与夏令时校验。

## 10. 非功能需求与验收

- 英文 UI；中文 PRD。日期基于伦敦时区，示例时钟与实际时钟分开标注；固定未来日期过期后须更新演示集。
- 目标手机390×844附近，保留模板iPhone/Pixel预览；关键按钮与输入不被底栏/键盘遮挡，长内容可滚动，键盘焦点可见。
- 交互使用语义按钮、输入标签与字段错误；状态通过文字表达，不只依赖颜色；动态消息有可访问提示；尊重减少动画设置。
- 所有核心按钮有实际结果；加载、成功、失败、空态与恢复有明确展示；后台多用户行为通过显式 Demo 工具触发。
- 无真实支付、卡信息输入、身份验证、实时库存、跨设备聊天或线上交易承诺。虚构头像/饭局必须用于演示；生成地图是示意图，无导航精度保证。
- 正式服务未来需补充运营规则、支付/预约供应商合同、隐私与留存制度、滥用防护及支持流程，不能用 Demo 的页面存在替代完成证据。
