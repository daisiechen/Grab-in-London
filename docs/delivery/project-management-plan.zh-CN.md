# Fancy 项目管理方案

修订：r05｜日期：2026-10-26｜面向：项目团队与worker｜状态：供用户审阅，未签发实施工作包。

## 1. 项目目标与本版范围

项目按[独立MVP需求](../product/fancy-requirements-baseline.zh-CN.md)交付iOS App和管理后台Web。移动Web后置：不启动其页面、响应式前台适配、Web分享、Web Push或新增Web业务测试。共享服务端仍可支持iOS和后台，不因接口经HTTP提供就视为在做移动Web。

M01—M12是业务模块，D01—D19是需求交付范围，r05是文档修订。D15/D19移至后续；D16保留iOS部分，取消其对D15实现的依赖，共用公开投影合同由D16工作包明确。Q-SHARE-01（未安装App者的邀请落地）未决，未解决前不能签收完整分享闭环，也不能据此自行开发移动Web。

原PRD/Demo唯一作者边界保持；本方案和产品需求由本会话维护，正式PRD/Demo的业务回填交原产出会话。本文规定团队怎样工作，不把团队岗位当作App用户角色。既有授权仍按实际范围执行，本文件不创建额外通用批准门槛，也不授权部署、模型费用或外发。

## 2. 项目团队职责与写入边界

| 交付角色 | 负责什么 | 边界 |
| --- | --- | --- |
| 项目协调负责人（PJ） | 范围、版本、依赖、任务签发、冲突处理与交付汇总 | 不代签专业审阅；未明确owner的文件不交worker自行抢写 |
| 产品经理（PM） | 将产品需求展开为流程、字段与PRD/Demo | 不用页面或现有代码反推需求，不直接扩产品范围 |
| 体验设计（UX） | 本版用户路径、必要状态、Figma节点/冻结版本与设计对照 | 复用有效稿；无需求依据不增加业务分支，不要求每页每错重复画稿 |
| 研发（RD） | 有界实现、接口/迁移/生成物协调、自测与精确提交 | 不同时写另一模块文件；共享生成物单一writer |
| 环境负责人 | iOS/后台最小运行入口、构建、角色/数据/时钟与故障工具 | 不让QA临场改账本/权限绕前置，不搭本版不需要的移动Web环境 |
| 质量验证（QA） | 独立模块及联合验收、分类缺陷、核对具体构建证据 | 不把作者自测或工具退出0当完整业务通过，不改变需求以消除失败 |
| worker | 在指定专业职责内完成一项有界任务 | 角色、可写文件、输入修订、完成标准均来自具体工作包，不继承全项目权限 |

访客、发起人、参加者是iOS产品角色；支持人员、分析者、数据管理员是内部业务使用者。即使同一个人兼任多个角色，产品访问权限和工程写入权限也不能互相推导。

## 3. 具体批次、执行顺序与PM限制

12模块保留60批MVP计划和后续移动Web4批；首发集合单独圈定为iOS40批、后台8批，递归依赖闭包48批，其余12批为后续增量。D01—D19只作需求追踪范围，具体签发单位改为M01-01等小批；不能把D01或整个模块作为PM一次自由展开的目标。

- [具体交付顺序与直接依赖](delivery-batches.zh-CN.md)：64批的默认顺序、跨模块最小合同、4个联合检查点、暂停/跳转边界。
- [产品分批功能范围](../product/mvp-batch-scope.zh-CN.md)：逐批目标、做什么、不做什么、可用前提与完成结果，不夹工程岗位。
- [批次数据](delivery-batches.json)：稳定ID、order、dependsOn、scope、验收映射、未决事项及未签发状态。
- [需求工程目录](requirements-catalog.json)：模块/D范围及业务背景依赖；真正开工依赖取批次DAG，不要求完整模块先全部通过。

**当前M01-01 PM-r01需求与Demo已成对交付待用户审阅，作者停止写入；其余63批未签发。允许阶段仅PM；用户先查看成对产物，再决定后续。UX、RD、QA及下一批均未启动。** 工作边界见[M01-01 PM工作包](work-packages/m01-01-pm.zh-CN.md)，实际阶段见批次数据。

后续有明确开工指令后，每批独立完成PM→UX→RD→QA；每泳道最多一个活动PM批次，隔离的iOS/后台泳道可并行。PM只展开本批需求增量、Demo及验收，不预写全模块。UX无新增画板也须明确复用核对，RD交精确候选，QA独立闭合后批次才ACCEPTED。返工回对应阶段并记录影响，不无差别重做所有阶段。

order为优先级/拓扑参考，不是全局串行锁。并行必须同时满足固定依赖合同、无重叠写集合、独立分支/worktree与运行/数据/时钟/配额隔离；公共鉴权/路由/store/契约/迁移/生成物/锁文件等有交集即串行交接。必要版本联调由独立集成工作区固定参与候选，失败回原批作者。具体阶段、并行、版本和回退规则见[逐批工作流与版本管理](batch-workflow-and-versioning.zh-CN.md)。

平台变更不删除历史Web证据，也不把它转作iOS证据。原Web/iOS联合断言中，本版iOS/后台适用部分按具体批次和I01—I04联验；确需移动Web的部分记录后续与新的关闭条件。原封存202/4/11不回写成通过。

## 4. 开工前必须明确的工作包

每份工作包写明发布集合归属、当前PM/UX/RD/QA阶段，并只引用一个具体批次ID及其产品范围，可细分安全代码提交，但不合并其他批次用户结果。跨模块最小合同按批次附件说明，不让worker自行补建整个相邻模块。

| 输入 | 必须写清的内容 | 信息缺失时 |
| --- | --- | --- |
| 目标与范围 | 模块/需求版/具体批次、具体用户问题、预期结果、本次不做事项及验收编号 | 交PJ/PM明确，不推演新功能 |
| 有效版本 | 需求包提交与模块路径、代码父提交、未提交清单、Figma命名版本/节点 | 不用“最新稿/之前讨论”代替；先核对来源 |
| 角色与文件 | 唯一实现作者、允许文件清单、共享契约/迁移/生成物writer、评审与QA责任人 | 不自动取得其他模块写权限；先交接 |
| 依赖与环境 | 输入/输出合同、最小角色/数据/时钟、运行入口、环境修复负责人、真实服务授权边界 | 仅阻塞相关断言，不扩建无关全平台 |
| 完成与回交 | 必须通过的路径、适用测试、确切提交/构建/环境、未测/阻塞、下一接收人 | 不把命令退出0或截图数量作为全部完成 |

本表是签发要求，不是已填好的授权。具体owner、白名单和Figma节点仍待原负责人盘点；本需求包未分派任何worker。

## 5. 专业交付的顺序与停止边界

1. **产品经理仅核对已签发小批。** 当前仅M01-01获PM授权；给出本批需求→用户行为→验收→现有PRD/Demo差异表；保留/修改/新增/范围外分别说明来源。正文保持当前有效规则，历史放来源记录，不用末尾附录覆盖冲突。
2. **体验设计交最小冻结稿。** 正常路径、必要失败/返回/取消、共享组件及节点映射齐全；无设计变更不重绘。新增字段/按钮/画板必须有本版需求依据。
3. **研发完成有界实现及自测。** 先代表页面/最短业务闭环对照冻结稿，再展开同类；跨模块契约和生成物串行交接，验证后回交精确提交。
4. **环境负责人交可用前置，QA验证。** 固定代码/构建/数据/时钟，不把真实账号就绪当业务门槛已通过。故障分类后交原owner，保留首次失败，模块验证后再做必要联合旅程。
5. **PJ收敛证据与未闭项。** 只在本工作包断言实际闭合时确认该范围完成；设计、模拟、真实依赖及发布各有状态，不互相替代。

同一文件同一时间一个writer，PRD/Demo原作者职责见[协作说明](../agent-collaboration.md)。文档编写授权不代替产品范围、真实费用或发布批准；不增加通用审批环节来代替已有有效授权。

## 6. 环境、验证与证据

本版原生构建/Xcode/签名与真机由Mac可用环境承担，首尔承担适用服务端和管理后台检查；不能把Linux构建通过称iOS设备已验收。仅准备当前工作包的固定提交/构建、角色、同库数据、必要时钟和故障入口。

QA先预检再业务验收。失败分类为产品缺陷、脚本故障、环境问题、需求歧义；交对应owner处理，独立用例可继续，相关断言保持阻塞。保留首次失败，不重复无变化的全量验证。模块通过后保留席位、授权、纠错/删除、统计与AI提交等必要跨模块验证。iOS双账号/双设备与后台联验替代本版本不要求的Web端执行；不同平台证据不得冒用。

状态分别记录需求已明确、设计已冻结、代码已交付、作者自测、独立验收、真实服务、发布，不用一个“完成”覆盖。模块产品验收编号对应下面的工程取证要求；历史详细标准保留，因本版平台变更而后置的断言单列，不假报通过。
