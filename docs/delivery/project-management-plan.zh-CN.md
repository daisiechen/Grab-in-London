执行修订：r09｜范围仍为r07；首发11份独立UX候选已交回待审，activeJourneys=[]；不自动进入RD或QA。

## 1. 当前交付单位

一份模块交付包必须回答“哪个用户，为什么来，从哪里开始，做完后得到什么结果”，从触发到成功终点及必要失败/返回完整闭合。不能将邮箱验证、资料表单、权限弹窗、单个后台页面或一个接口单独作为PM业务模块。

本项目当前模块为[15个用户旅程](../product/journey-modules.zh-CN.md)，状态/合同/联调以[旅程执行方案](journey-execution.zh-CN.md)及[执行数据](journey-execution.json)为准。旧M01—M12领域划分、D编号和60个小批降为历史能力/实现清单，禁止继续按它们派PM；技术上可细分代码任务，但不拆开需求/Demo的用户体验。

首个产品交付包应为**J01找到并申请一场合适的饭局**：浏览/筛选/详情→需要参与时完整注册或登录→必要资料→回同一饭局→主动申请→可追踪待审/撤回。用户不需要注册时仍能先浏览。新老账号、邮箱/Google/Apple是同一旅程的分支，不能为了控制工作量把注册后半段留成“下批再做”。

J01不代替发起人审批，也不开发整个个人设置或已确认群沟通；这些是另一个用户目标。Demo允许模拟外部角色/数据前置，但必须在该用户的自然路径走到申请结果，不能在资料入口中断后宣称闭环。真实联调另行取证。

## 2. 项目团队职责

| 交付角色 | 负责什么 | 边界 |
| --- | --- | --- |
| 项目协调负责人（PJ） | 范围、版本、依赖、任务签发、冲突处理与交付汇总 | 不代签专业审阅；未明确owner的文件不交worker自行抢写 |
| 产品经理（PM） | 将产品需求展开为流程、字段与PRD/Demo | 不用页面或现有代码反推需求，不直接扩产品范围 |
| 体验设计（UX） | 本版用户路径、必要状态、Figma节点/冻结版本与设计对照 | 复用有效稿；无需求依据不增加业务分支，不要求每页每错重复画稿 |
| 研发（RD） | 有界实现、接口/迁移/生成物协调、自测与精确提交 | 不同时写另一模块文件；共享生成物单一writer |
| 环境负责人 | iOS/后台最小运行入口、构建、角色/数据/时钟与故障工具 | 不让QA临场改账本/权限绕前置，不搭本版不需要的移动Web环境 |
| 质量验证（QA） | 独立模块及联合验收、分类缺陷、核对具体构建证据 | 不把作者自测或工具退出0当完整业务通过，不改变需求以消除失败 |
| worker | 在指定专业职责内完成一项有界任务 | 角色、可写文件、输入修订、完成标准均来自具体工作包，不继承全项目权限 |


以上是项目交付岗位，不是App产品角色；产品使用者与权限只写在MVP需求。各旅程PM及UX作者已分别登记，原主PRD/Demo和共享文件唯一owner规则不变，迁移产物先交接。

## 3. 每个旅程独立PM→UX→RD→QA

| 阶段 | 本旅程交付与完成边界 |
| --- | --- |
| PM | 完整目标/角色/触发/步骤/终点、必要异常/取消、分支、业务规则来源、现状差异和成对Demo；不只写页面字段，也不顺手展开其他目标 |
| UX | 以同版PM路径核对现有设计并补必要差异，固定Figma版本/节点；无新画板也给明确复用核对，不机械扩每页错误稿 |
| RD | 先固定共用合同与本旅程文件owner，再分技术任务实现；代码可分多提交，旅程业务结果不按技术子任务分裂验收 |
| QA | 对精确候选独立验证完整自然路径和恢复，再补涉及其他旅程的联合断言；作者自测不算独立QA，模拟不关闭真实门槛 |

发现规则问题回PM、表达问题回UX、实现问题回RD、环境问题交环境owner；只使受影响下游证据失效，不每次重跑全部项目。缺输入不能由worker新增业务规则。当前仅签发UX设计；以固定PM输入制作，不改旧Demo，不启动RD/QA。

## 4. 顺序、依赖与并行

建议先确认J01，再梳理J02/J03的同一招募沟通链，随后J04/J05/J06、J07/J08/J09；后台J10/J11可在固定数据合同下并行准备。数字是规划优先级，不是整模块完成依赖或全局串行锁。

身份/公开饭局/席位/消息/反馈/支持/统计/AI/通知是共用技术能力，按C合同登记单writer及版本。J01消费饭局并产申请，J02消费申请并产饭局，这是真实双向业务关系，不能设置“J01全做完才能J02，而J02全做完才能J01”的环。

PM可在明确合成前置和固定合同下表达完整本用户路径；RD接固定兼容输入，QA必须在实际前置或联合组中闭合业务证据。假定另一角色已经操作只属于模拟，不冒称真实业务完成。每个技术任务都挂回旅程的验收结果。

并行要同时满足固定合同、不同文件写集合、独立分支/worktree、环境/数据库/账号/时钟/配额隔离。公用鉴权/路由/store/迁移/生成/锁文件交叉即串行交接。删除/调钟/故障注入不得共享破坏性数据。iOS与后台可分泳道，无干扰的专业阶段可流水，但同旅程不能省阶段或自审自签。

联调固定iOS build、后台hash、API/worker SHA、契约/迁移/数据版本。只联验业务边界及共享状态，问题回原旅程owner，集成负责人不取得全项目自由改写权。具体T-MEET/T-AFTER/T-SAFETY/T-REMIND组见执行附件。

## 5. 首发集合与版本管理

首发iOS为J01—J08及支持运营J09；首发管理后台为J10/J11。J12体验与留存、J13邀请、J14提及送达、J15免打扰是后续增量，移动Web继续后置。按原能力清单映射，首发保留原48个必要功能切片的能力，后续4旅程覆盖原12增量，不因改名取消原要求。

AI在J01选饭/申请、J02创建、J03群沟通中交付，真实模型/数据/成本门槛仍在首发，不缩成假助手。账号删除、举报处理和屏蔽/内容治理条件仍是首次上架门槛。Apple适用核查沿用[已核查资料](release-sets.zh-CN.md#4-app-store适用要求核查)，其中旧切片集合不再是当前派单依据。集合明确不保证上架/上线，releaseApproved均为false。

需求修订r07、旅程PM修订、Figma引用、工程提交、运行候选及发布版本分别记录；保留既有历史和未批准候选。每旅程可独立分支/提交，公共契约与迁移单writer；合并前核代码/合同/产物依赖，迁移回退与代码回退分开，不删库回滚。实际发布仍需精确候选、适用真实门槛和明确发布授权。

## 8. 逐条范围审计与防遗漏门禁（r07）

范围附件为[完整核对报告](../product/requirements-audit.zh-CN.md)、[原文逐条映射](../product/requirements-traceability.zh-CN.md)及[机器台账](../product/requirements-traceability.json)。本轮PJ写入范围为统筹规划、索引、交付汇总与验证；UX只写各自设计交付目录及对应测试；原主PRD、补丁PRD、原Demo及后台作者文件保持只读。任何源文档变更使对应hash/行映射失效，须先核对新增、删除及改义，不得直接更新hash掩盖差异。

后续签发一份旅程工作包前，PJ从台账筛选该旅程＋具体版本的全部有效条款，将原FR/AC/PATCH/D-AC、关键字段/状态/权限/恢复、共用约束和未决项一并交给PM。PM交付须回填每条在PRD章节、Demo场景的对应位置；UX补Figma节点/冻结版本，RD补实现候选，QA补独立场景/证据。范围台账记录归属，现已另有逐旅程PM需求/Demo和映射；UX按当前派工补节点，尚未形成RD/QA产物。有映射不等于可验收。

全量MVP、最小首发及后置范围各自列清；不得在重拆旅程时自行移动版本。任何延期/取消/替代都要记录原需求ID、旧/新版本、原因和批准依据。非功能、真实服务/政策/成本门槛随消费旅程进入同版验收；J12后置不能删首发概览指标，J14后置不能删首发业务邮件，AI偏好/生命周期不能漏在“融入”二字中。

验证使用原文完整性、原验收编号/切片覆盖、旅程/版本引用、重点规则回归及不开工状态检查。静态测试不能证明语义全无歧义或产品可上线。任何缺少归属、版本、有效性说明的条款禁止进入下游；同一条多旅程消费须写清首次实现和后续消费边界，避免重复建设。
