# r11 版本PJ并行推进与发布管理

本轮用户明确要求每个版本独立推进。由[执行登记](execution-r11.json)记录当前状态；r10保留版本范围和原始交付证据，原“7份Figma全部Ready才推进”总门槛被本文件替代。总PJ不再逐项代理版本执行。

## 责任与推进

| 版本PJ | 独立版本 | 设计复验人 |
| --- | --- | --- |
| PJ-IOS1 | IOS-0.1.0-dev.1；相关DS规范 | PJ-IOS2 |
| PJ-IOS-DEV2 | IOS-0.1.0-dev.2，独立工程/台账writer；原Figma作者仍UX-2 | 设计PJ-ADMIN；工程独立RD |
| PJ-IOS2 | IOS-0.1.0-dev.3、dev.4，各自台账与方案 | 设计PJ-IOS1；工程独立RD |
| PJ-ADMIN | SUPPORT-0.1.0-dev.1、ADMIN-0.1.0-dev.1/dev.2，各自台账与方案 | 总PJ独立复验设计 |

I2设计签收后，原writer明确停止工程/台账写入，再由新版本PJ接管；不为换人重做已通过设计。四个PJ按任务与可用执行位排班，等待外部工具或独立复核时释放执行位，不空转占用。

每版独立组织设计审查、原作者修复、独立复验、开发方案与测试矩阵；修复与复验直接交接，不经总PJ逐条转发。原作者不能自签通过。每版通过本版设计与适用DS组件核对后即可进入本版开发方案，不等待其他版或整套组件库。真实依赖只阻断使用该依赖的集成或测试点，其他准备工作继续。

版本PJ在`docs/delivery/versions/<version>/`维护状态、问题、下一步与证据，在`docs/engineering/r11/<version>/`交开发方案；每版独立文件负责人，不共享可变大任务表。总PJ登记版本范围、共享契约writer、冲突、跨版联调、合并发布及Git。当前授权是评审修复与通过后的开发方案；未签发业务实现，不把设计走查叫产品QA。

## 每版交付与测试

每个版本的开发方案必须给出：用户完整旅程、做/不做范围、精确输入/设计修订、模块接口与数据权威、可独立验证的小工作包、文件负责人和写入范围、环境最小预检、单版用例与受影响回归、跨版契约/联调前置、回退办法。既有r10架构可参考，不重新搭整个项目或复制全部需求。

状态分别记录设计、方案、代码、单版测试、联调、合并、部署与商店提交；必须绑定候选SHA/build/接口/迁移/数据/环境。Mock、原型、真实服务证据分开。某版完成不能清除另一版未完成状态；上游没有实现时可以核对合同、使用明确夹具验证本模块，但不声称真实联调通过。

用户后续按版本追问时，版本PJ直接提供本版已完成、正在做、真正阻塞、下一步和证据。总PJ汇总差异，不重新串行执行其全部任务。

## 分支、合并与部署

从已核对的main创建`codex/<product>-<version>-dev<N>-<module>`短分支或独立worktree。一个分支绑定明确版本/小包，契约、迁移、生成客户端和导航/根配置各有唯一writer，跨版本变更需共同候选核对。禁止直接在main开发，禁止把无关研究和旧QA未提交内容混入。

完成适用单版测试、受影响回归、独立代码评审及所需CI后，通过PR合并main；不能以本地某个单测绿代替全部必需检查。部署仅来自精确合并SHA与对应已测构建，记录迁移/环境/部署结果；文档合并不自动触发业务部署。设计修复也在本轮分支记录，核对与适用验证后才能集成。共享工作区当前由总PJ唯一操作Git索引，版本PJ仅交白名单与验证结果。

## 首个iOS商店版本与后续节奏

内部dev.1仍只是发现/完整注册/申请与设置，不包含完整招募沟通、安全和删除，因此先独立开发测试，不能直接等同商店首发。用户允许合并发布，首个商店候选0.1.0合并四个iOS迭代和最小支持能力；不是要求这些版本等待彼此才开始工作。候选完整、真机/真实服务/隐私与商店资料等门槛通过后，按用户要求尝试上架，不提前承诺审核通过。后台仍按其两个内部版本独立开发、测试与部署候选，真实跨域数据与隐私传播另行闭环。

每个完成的iOS迭代都登记build及目标商店版本；可以单独提审或并入明确后续发布批次，不能悄悄遗漏。当前0.1.0内部里程碑不各自递增产品功能版本；首发后的同范围修复用0.1.x，既定分享/邀请0.2.0与提醒等0.3.0保留原范围。管理员或服务端单独变化不无故提交空iOS更新。

2026-10-27核对Apple官方说明：新商店版本需递增版本号，上传需递增build；创建下一商店版本有当前版本状态前置。[创建新版本](https://developer.apple.com/help/app-store-connect/update-your-app/create-a-new-version)。通常同平台一次提交一个审核批次，不能把可额外提交其他内容误解为多份App版本同时审。[审核提交说明](https://developer.apple.com/help/app-store-connect/manage-submissions-to-app-review/overview-of-submitting-for-review)。本次查阅未发现通用“必须间隔N天更新”的固定要求，不编造每周或每月上限；根据实际审核状态、稳定性、变更规模合并提审。

Apple的7天是可选的自动更新分阶段发布安排，期间用户仍可手动下载，不能当成提交频率限制。[分阶段发布](https://developer.apple.com/help/app-store-connect/update-your-app/release-a-version-update-in-phases)。首发保留完整性、真实后端可达、UGC处理/举报/拉黑/联系方式及应用内账号删除等适用检查，发现缺项记录到发布门槛并交对应PM/版本负责人，不把后端未接入混成视觉失败。[审核指南](https://developer.apple.com/app-store/review/guidelines/)。
