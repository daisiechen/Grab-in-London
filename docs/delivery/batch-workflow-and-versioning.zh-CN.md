# Fancy完整旅程的工作流与版本管理

修订：r10｜当前按[开发版本方案](development-versions-r10.zh-CN.md)复用原MVP设计并分dev迭代；旧60切片不再派发。

## 1. 交付包边界

交付包按用户一次完整操作目标划分，见[15个产品旅程](../product/journey-modules.zh-CN.md)。PM说明/Demo必须贯穿触发、必要认证注册/资料、用户操作、成功终点和失败/返回；不把其中一页或一个接口当完成成果。旧M01-01只登录Demo留作历史，不进入新旅程的批准或研发队列。

## 2. 独立四阶段

每旅程独立PM→UX→RD→QA。PM交完整路径、业务分支、规则/验收、现状差异和Demo；UX核对同一输入及冻结设计，必要时复用而不扩图；RD可按文件/接口细分任务但挂回同一用户结果；QA先正常完整路径及必要恢复，再关联旅程联调。具体职责见[管理方案](project-management-plan.zh-CN.md)。

同一旅程只一个活动阶段；作者自检不是独立QA，阶段输出固定修订/证据。返工按规则/设计/实现/环境分类回原owner，只使受影响下游失效，保留旧意见及失败，不无条件重跑全项目。当前首发PM业务输入固定，UX按r10复用原MVP视觉；RD架构准备可并行，逐模块业务实现和QA仍not-started，不自动晋级。

## 3. 共用合同与并行

[执行方案](journey-execution.zh-CN.md)区分固定合同输入和双向业务联调。J01需要饭局供给，J02需要申请者，这不意味着必须等对方整个模块完成。PM可在明确合成前置下表达自身完整旅程，真实通过仍须T-MEET实际闭合，不能把合成当生产证据。

无干扰旅程/专业阶段可并行：固定输入修订、无文件写集合交集、独立分支/worktree/数据库/账号/时钟/端口/配额。公共鉴权/路由/store/组件、契约生成/迁移/worker入口/锁文件有交集即单writer串行交接。仅模块名、分支或agent不同不能证明无干扰。

PM只展开签发的一个完整旅程，不预写全项目；iOS/后台可独立泳道准备，但不让QA删除/调钟/故障注入污染其他现场。前置不齐记阻塞，由PJ在有效授权内选择独立工作，不由worker自行扩范围。

## 4. 版本、联调和回退

需求总修订r07、单旅程PM修订、UX Figma命名版本/节点、代码提交和运行候选分别登记。新工作包需唯一作者/独立核对者、准确输入、允许文件、共享writer、数据与环境、完成标准及下一接收人；当前不填造owner或假签收。

每旅程可独立分支/多个技术提交。公共合同原owner交固定SHA及diff→接收方核兼容→统一生成/构建→回交固定SHA。主分支不得混入缺依赖的中间状态或其他未提交工作。

T-MEET等联调使用单独集成工作区，固定iOS build/后台hash/API-worker SHA/契约与迁移/数据版本；问题回旅程作者，不赋集成人全项目写权限。变更只补影响回归，不能拼接不兼容构建证据称通过。

iOS和后台分别保留产品版本、候选、发布批准及回执，当前都未发布。已有0.1.0候选仅规划标识；不自动创建tag或改配置。代码回退优先revert，数据库迁移需兼容/前向修复/独立恢复方案，不删库回滚。源、产物、证据相互可追溯后再按实际授权发布。
