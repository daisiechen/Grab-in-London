# Fancy逐批工作流、并行与版本管理

修订：r05｜面向项目团队｜适用于本版60批、后续Web4批及有界纠偏工作包。

## 1. 每个批次都有独立PM、UX、RD、QA

| 阶段 | 本批输入 | 本批输出与离开条件 |
| --- | --- | --- |
| PM | 批次ID/做与不做/验收、固定业务基线、直接前置合同和已有产物 | 仅本批需求增量、自然路径/关键恢复、需求到验收映射、与现状差异及Demo表达；范围核对后冻结PM修订 |
| UX | 同一批次已冻结PM修订及现有设计 | 仅本批设计差异、Figma版本/节点、必要状态及对照证据；独立核对后冻结UX输入 |
| RD | 同批PM/UX冻结输入、兼容契约/前置候选、代码基线、唯一文件白名单 | 只改本批、按需拆提交、自测及代码审阅、产物/迁移/契约说明与QA包；不能用未提交目录交付 |
| QA | 同批输入和精确候选构建、最小可用前置、环境负责人及断言 | 独立执行并分PASS/FAIL/BLOCKED/NOT_RUN，复验修复与影响回归；适用断言闭合才将本批记ACCEPTED |

每批依次走四阶段，不能用其他批的PM/UX或整模块总验收替代。本批无需新增画板时，UX仍给出“复用哪些冻结节点、为何无变更、如何核对”的具体审查结果；不是省略UX。已有实现可继承，但每批仍核对当前输入/产物/证据是否适用，不强迫重做。

PM只对签发的本批展开，不一次写全模块或全部首发。产品角色与用户行为仅写在MVP需求及附件；项目人员、文件边界、工具与验证写在管理方案/工作包。

## 2. 状态与返工

每批记录currentStage和PM/UX/RD/QA各自状态、输入修订、输出修订和证据引用，阶段状态可为not-started/in-progress/in-review/passed/failed/blocked。当前仅M01-01处于PM阶段，其他批次及所有UX/RD/QA阶段均未启动。

同批只允许一个活动阶段；只有当前阶段输出在固定输入下通过核对才进入下一阶段。RD→QA不得省去代码审阅；作者自测不能充当独立QA。QA发现产品规则歧义回PM，设计表达问题回UX，实现问题回RD，环境故障交环境owner并保持QA blocked。

返工使受影响的下游修订/证据失效，必须记录影响清单，只补受影响阶段和断言；不删除旧意见，不每次无差别重跑全批。一个候选含未接受批次的代码时，不能把该批标已交付或让首发无意暴露其入口。

## 3. 允许无干扰批次并行

order是优先级/拓扑参考，不再是全局串行锁。初始以iOS与admin-web两条交付泳道组织；每条泳道最多一个活动PM批次，不同泳道可同时进行PM，后续专业阶段也可流水并行。新泳道需PJ明确容量及隔离，不自动无限增worker。

并行同时满足：

1. 前置合同已有固定可读修订；PM可基于冻结合同准备下一批，不宣称前置功能已验收。RD需兼容前置实现候选，QA闭合需前置实际可运行并已验收，或在明确的联调组中一并通过。
2. 有不同的唯一作者、独立分支/worktree、无重叠文件写集合；全局store/路由/鉴权/公共组件/合同生成/迁移/worker入口/锁文件重叠即暂停相应写入，先串行交接。
3. 环境/数据库/schema/种子数据/账号会话/测试钟/端口/临时文件及外部配额独立。删除/时间推进/故障注入不得作用在另批使用中的现场。
4. 需求/设计/代码输入固定，双方明确接收对象与结束条件；共享服务变更有版本兼容证据。仅模块ID不同、分支名不同或agent不同均不足以认定无干扰。

候选示例：M02-02筛选与M03-01选店在身份/合同就绪且iOS公共状态不重叠时可分工作区；M06-04产品问卷与M08-03用户旅程在后台输入已冻结且数据隔离时可分泳道。均为条件示例，非现在派单。M01-02和M01-03虽无彼此业务依赖，若共用登录文件/回调则串行；M08-06分类与M08-07刷新有直接依赖，不同时写同一合同；QA删除与其他同库旅程绝不并行破坏数据。

当前只允许M01-01的PM需求＋Demo任务；并行规则不扩展这次授权，不自行唤醒其他批次或UX/RD/QA。

## 4. 版本与集成管理

| 对象 | 记录与管理方式 |
| --- | --- |
| 产品/发布集合 | IOS-MIN-01、ADMIN-MIN-01与各自候选0.1.0；独立发布批准/回执，当前仅规划，不改App配置或创建tag |
| 需求批次 | r05总输入＋批次ID＋PM本批修订；冻结后实质范围变化回PM并列影响，不在聊天里口头覆盖 |
| 设计 | 同批UX修订＋Figma文件/命名版本/节点，复用时也记录精确引用 |
| 工程 | 分支可用codex/batch-m02-02等；每批独立提交/PR或明确提交白名单，公共契约/迁移生成单writer串行 |
| 运行候选 | iOS build/commit、后台静态产物hash、API/worker SHA、契约与迁移版本、依赖锁文件hash及环境ID |
| 验证与发布 | QA绑定上述候选；候选变化做影响分析。iOS/admin可分别使用ios/v0.1.0-rc.1、admin/v0.1.0-rc.1作为未来候选标签建议，未实际创建 |

主分支不合入缺依赖中间状态，不因工作区存在就继承其未提交代码。共享文件串行集成：原owner交固定提交及契约diff→接收方核兼容→更新生成物/构建→回交固定SHA→运行适用验证。互相依赖提交需形成可验证原子集成，不能混入别的未完成改动。

版本间联调使用单独的集成分支/工作区及隔离数据，登记参与批次和精确候选组合；只测接口、状态传播和共同旅程，不把联调环境变成所有worker的共享写工作区。通过后由集成owner按白名单串行合并/提交/推送/核远程；产品/模块owner不因联调转移。

回退优先revert本批提交；数据库迁移有独立兼容/回退或前向修复方案，禁止为回滚代码直接删库或退回已迁移schema。部署前另有备份/恢复及授权，不在本轮执行。保持旧客户端与新服务契约兼容，不能用只升级UI规避权限/数据迁移问题。

## 5. 签发时的运行清单

每份工作包补齐：批次/发布集合归属、当前阶段、唯一作者与独立核对者、输入修订、分支/允许文件/共享writer、前置与联调组、运行环境/数据/时钟/配额、产物与证据、下一接收人及停止条件。并行时登记活动批次和资源占用；冲突先停止相应写入再交接，不靠超时推定旧作者已停。

状态清单不得用QUEUED当开工、进程结束当验收、QA通过当发布。当前activeBatches=[M01-01]，只进行PM需求与Demo，未批准UX/RD/QA或发布；具体状态以批次数据及PM工作包为准。
