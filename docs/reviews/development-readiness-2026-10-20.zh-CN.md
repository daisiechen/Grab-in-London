### B-01：先确定本次“开发”的范围，保留完整 Demo

**证据**：[主 PRD](../product/PRD.zh-CN.md)第3–5行、§11第407–415行：正文以高保真 Demo 为阶段；当前 Demo 包含2–6人、应用内支付和订位，真实 R1 仅为“方向已讨论”的3–6人、外订和线下结算；正式资料门槛、最低成团与截止仍列为待评审。后台 PRD §1、§4却以真实试点结果为目标。

**场景与分歧**：研发按主体规格设计付款账本、供应商预约与双人桌；另一团队按 R1 只做外订线下付。两者均能找到原文支持，却会得到不同的数据、服务边界、权限、页面与验收范围。

**最小补充**：新增一份由产品确认的范围映射，逐模块说明首期实现、保留为后续参考、明确不做的能力；明确首期客户端平台和后台实际使用角色。完整 Demo 可原样保留，不需要以缩减或重构 Demo 来澄清范围。Demo默认参数可以被正式采用，也可以替换，但须写明采用哪组规则。

**关闭条件**：两个原会话引用同一张范围表；研发能对“双人、预付、代订、出席、整场反馈、举报处理、账号生命周期”分别得到唯一首期答案。若预付/代订不在首期，对应交易细化移入后续，不强制先设计后续完整财务系统。

### B-02：遗留契约不能自动填补恢复版需求

**证据**：[索引](../README.md)仍将[shared 契约](../../shared/README.md)列为研发契约；shared 第14、17、54、60行分别规定“本人优先、无人工核实”、举报处置、JSON导入导出、future入口。而[后台 PRD](../product/admin/PRD.zh-CN.md)第9、26–32、79–89行定义核实者与冲突核实、不设计安全管理；[App入口](../../demo/src/App.tsx)只引入 Prototype；当前后台 `admin/src/handoff.ts` 在工作区已删除。

**场景与分歧**：一组研发以 shared 作为已批准规则，采用本人优先和创始人全权后台；另一组遵循当前后台 PRD，采用冲突核实和分析者/核实者权限。两种产品的出席权威与隐私访问完全不同。

**最小补充**：明确 shared 各部分是历史参考、待议方案还是现行契约；只保留明确确认过的规则作为真源，修正索引和对应链接。不能通过重新接入旧模型来“修好”需求。

**关闭条件**：主 PRD、后台 PRD、索引、shared 的权威关系一致；选定的出席/权限/交接方式不相互否定。模拟 JSON 传递不是必须能力；若不需要，将其明确为历史材料即可。

### B-03：实际出席必须有共同的业务事实与修订规则

**证据**：主 PRD FR-10第303–307行要求“实际同桌”“未出席不能评价”，但没有定义如何产生实际出席事实。后台 PRD第81–89行及采集契约第43–45、93行规定计划结束=开始后2小时、本人/host报告、冲突核实与7天窗口，且称入口已新增。当前 [饭后页代码](../../demo/src/Prototype.tsx)第3390–3510行没有出席报告控件。shared第14行的本人优先又与冲突规则相反。

**场景与分歧**：host说出席、本人说未出席；或运营已核实后本人再改口。一种实现保留核实结果，另一种重开冲突；用户能否评价、互选和私聊，以及后台出席人数都会不同。只有“服务端校验实际同桌”不足以回答校验依据。

**最小补充**：主 PRD定义资格名单、完成时点、报告入口与操作者、本人/host/核实的优先及更正规则、7天边界等号、窗口后纠错；明确资格变化后已有公评、整场反馈、互选关系如何处理。后台引用同一规则。真实任务调度和存储实现留给研发。

**关闭条件**：推演未报、单方、冲突、核实后再报、开饭时退出、窗口刚到、纠错后反馈失效的结果；用同一用户/饭局对照用户可操作项和后台统计。只有选定的关键出席交互需要最小局部 Demo 表达，不要求建设生产采集。

### B-04：整场体验与针对某个人的意愿不是同一对象

**证据**：后台 PRD第135–142、258行及采集契约第46行称 P-11 已有私密1–5评分、再次参加 Fancy 意愿及多选原因。主 PRD FR-10仅定义公开文字和个人再约，写“无综合星级”；Prototype第3413–3451行只有公评与“I’d like to share a table again”。当前不能判断“无综合星级”仅指个人，还是也排除整场私密评分。

**场景与分歧**：用户不想再见某个人，但愿意再参加 Fancy。把个人 wants 当作 again 会报成不愿再来；新建整场反馈则需要独立对象、资格和入口。

**最小补充**：在主 PRD明确个人公评、私人再约、整场体验三者的关系；若首期保留整场体验，定义评分/again必填、原因枚举、更新和截止、隐私读者及入口；后台引用。若首期不采集，移除相应指标的首期承诺并显示未就绪，不以公评推导。

**关闭条件**：能表达“喜欢饭局但不想再见该成员”和“未反馈”两种不同结果；同人同场更新不重计；主 PRD、实际页面及后台字典一致。不能仅修正文案“已新增”而保留没有来源的首期指标承诺。

### B-05：低于最低人数后的终局与外订责任未定

**证据**：主 PRD FR-06第253–254行、FR-08第268行和E-12要求至少3人且不能自动变双人，却只给出“重订/补员/取消”几个方向；§11仍把最低人数与自动取消截止列为未决。创建第236行按总人数外订声明；后续有人退出时未定义何时声明失效。采集契约第42行明确未达标不自动等于取消。

**场景与分歧**：4人桌开饭前减到2人，host没有回应。一种实现按时取消并退款，另一种保持进行并允许出席；若外订4人已确认，人数减少后是否仍向成员展示有效预约也不同。

**最小补充**：定义申请/审核/招募截止、最低人数检查时点、低人数能否继续及谁决定、无响应默认结果、外订人数变更责任与声明有效性；明确通知对象。无需预定采用历史 shared 的60/45/30/15规则。

**关闭条件**：对始终不足、达标后减员、截止瞬间补员、外订人数变化、host无回应、开始后取消逐一得到确定的饭局/席位/预约/出席资格结果。收费路径若在范围内，同时核对退款责任；若不在首期，不扩展财务设计。

### B-06：申请生命周期及“新申请”边界需要明确

**证据**：主 PRD第221行付款保留30分钟但不晚于“申请截止”，没有给申请截止定义；第316行列EXPIRED。第481行允许撤回重新申请，但未定义新轮次。当前 [domain](../../demo/src/domain.ts)第304–325行允许WITHDRAWN重申、拒绝其他非NONE状态，JoinState第1–8行无EXPIRED；后台以applicationId统计，第120–122行跟踪获准/确认/出席及待审核耗时。

**场景与分歧**：A撤回后重新申请并获准。覆盖原记录会把审核耗时从首次申请算起；新建轮次则保留一次撤回和一次获准。获准待付款能否撤回、已取消参与能否重入、被拒后能否再次申请、临时席位到期后是否重新排队也无完整正文规则。

**最小补充**：给出状态×允许动作表、绝对截止及等号、重申资格、轮次ID、有效席位唯一性、历史聊天可读区间与通知；规定当前状态与历史漏斗是否区分。

**关闭条件**：撤回→重申、拒绝→重申、付款过期→重申、确认→退出→重入均有唯一结果；同人同场申请记录与参与人次按各自单位核对，不以旧单测结果关闭本问题。

### B-07：改期不能只写“需要重新确认”

**证据**：主 PRD第247、370行要求发布后时间/地点/费用变化重新确认；失败替代时段在第501行允许恢复。但 [Prototype](../../demo/src/Prototype.tsx)第2152–2168行 host 选择替代时段会直接改整桌时间并标CONFIRMED，没有成员重新确认。§12承认关键字段编辑未完整覆盖。

**场景与分歧**：已确认成员接受19:00，host改19:30。一种实现维持所有成员确认，另一种撤回旧确认等待答复；名额、外订人数、退款与群聊权限都会不同。

**最小补充**：明确首期是否禁止发布后关键编辑；若禁止，说明失败恢复走取消重建或哪种受限流程。若允许，定义谁需重新确认、答复截止、拒绝/沉默结果、原席位和原安排何时失效。备选时段计算本身属于工程实现。

**关闭条件**：同意、拒绝、沉默、改期时同时退出各有确定结果；Demo仅补必要局部确认表达或明确不承担该流程，不要求重做创建与详情。

### B-08：互选与屏蔽后的联系授权没有完整生命周期

**证据**：主 PRD第298、303–307、495行写拉黑阻止联系、解除不跳过互选；未说明互选能否撤回、是否按人或按饭局、旧私聊可读范围。[Prototype](../../demo/src/Prototype.tsx)第976–979行使用单组review/wants/mutual状态，第2211行以mutual与blocked决定私聊访问；第2835–2845行换反馈上下文会重置这些状态。shared第16行另有撤回和跨场清理规则，尚不能视为恢复版已采用决定。

**场景与分歧**：A/B在两场饭局互选，A后来撤回一次或屏蔽再解除。一种实现恢复原联系，另一种要求重选；旧私聊隐藏还是只读也会不同。

**最小补充**：定义同意的作用域、变更/撤回及截止、屏蔽对双方同意和历史消息的影响、解除后恢复条件。若首期明确不提供撤回，也需写明可用的撤销联系方式与授权含义。

**关闭条件**：两位不同联系人、同一联系人跨两场、单方撤回、拉黑解除均不会误开其他人的私聊；过去内容与未来发送分别有确定权限。无需更换整个聊天界面。

### B-09：“申请→出席”成熟时点有两种规格

**证据**：后台 PRD第121行写“已结束至少24小时”，第81行结束是开始后2小时；采集契约第66行及 [analytics](../../admin/src/analytics.ts)第573–577行按“开始后24小时”。两者分别是T+26小时、T+24小时。

**场景与分歧**：18:00开始、20:00结束的饭局，在次日19:00快照。一种实现已进入漏斗分母，另一种仍观察中；同一份数据得出不同结果。

**最小补充**：负责人选定以开始或结束起算，同步PRD、契约、字典、界面解释及测试；顺带说明成熟后出席记录是否随7天内补报回补，避免把成熟时点误读为冻结结果。

**关闭条件**：以T+24、T+25、T+26小时及边界等号手算，对照查询/UI/导出一致；明确迟到报告只改变新快照。

### B-10：游客可见权限不能只由 Demo 的预登录能力决定

**证据**：主 PRD §3.2第79行写公开饭局、主页与评价“登录可见；Demo预登录”，FR-11第175行则写游客可看地图、详情和公开主页。前者可理解为正式产品需要登录，后者可理解为游客正式开放。当前domain第486–497行与页面门禁允许游客浏览，不足以证明正式权限决定。

**场景与分歧**：未登录者直接打开成员主页链接。一种实现返回登录门禁，另一种返回公开投影；会改变缓存、发现查询、资料接口与隐私承诺。

**最小补充**：明确正式游客可访问页面及字段，与已登录者的差异；把仅Demo放开的例外单独注明。无需增加新的注册流程或修改现有视觉。

**关闭条件**：主PRD权限表与入口规则一致；游客直接访问饭局/成员主页、受限操作回流各有确定结果。两端后台人员不因公开主页可见而获得更多私密信息权限。

### B-11：整场取消需要独立于本人退出与餐厅预约取消

**证据**：主PRD FR-08第263–268行说发起人取消会影响全部成员，但没给允许取消的阶段及开始后处理；§7第315、317行同时存在Meal和Reservation的CANCELLED。后台PRD第105行、采集契约第70行要按整场原因统计，主PRD没有约定原因集合与采集人。当前domain第533–535行用booking CANCELLED决定当前成员群聊只读；Prototype第1152–1184行是个人退出，主持页第3512行起只有申请处理，不能表达整场取消的完整影响。

**场景与分歧**：host取消餐厅预约准备重订，是否应归档整个群并计入饭局取消？饭局已开始后host取消，是否剥夺已同桌者饭后资格？没有共同业务定义会使一端统计取消、另一端仍判断有效出席。

**最小补充**：主PRD分别定义撤回申请、个人退出、整场取消、预约取消/失败；对整场取消写明操作者、允许时机、终态、名额、待审申请、群聊、出席和通知结果；确定后台原因枚举及未知含义。收费在首期范围内时再补退款责任矩阵，不强制采用现有示例为正式政策。

**关闭条件**：个人退出不取消整场；餐厅重订不误归档群；整场取消能传播到全部受影响成员及分析结果；开始后请求有明确结果；原因可采集且两端一致。Demo只需表达必要的取消确认和结果，不要求实现真实批量退款。
