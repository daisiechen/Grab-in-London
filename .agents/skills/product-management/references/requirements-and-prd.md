# 需求与PRD

## 选择交付深度

- Brief：对齐问题、目标、对象和方向，不伪装成可开发规格。
- 决策型PRD：支持范围与方案选择，明确假设和首个可验证版本。
- 开发交付版PRD：补齐实现所需的业务规则、路径、状态与验收，不要求研发猜测关键行为。

根据任务明确交付深度。文档面向没有读过聊天历史的协作者，使用完整、当前有效的叙述；变更历史不替代更新正文。

## 开发交付版结构

按实际需要覆盖：需求背景与证据、产品目标与设计原则、用户与角色、用户路径、模块职责、功能设计、非功能要求、验收标准、版本边界、依赖和未决事项。简单功能可合并章节，不填充无内容的模板栏位。

目标应能对应用户结果与衡量方式；明确不做什么、当前原型覆盖什么，以及真实实现分期，避免把未来规划写成已承诺能力。

## 用户路径与模块

从触发、进入、理解、操作、反馈、完成到后续回访梳理路径，覆盖实际不同角色和有显著差异的首次/再次使用场景。每一步说明用户目的、所需信息、障碍和下一步。

软件产品按职责划分前端体验模块、后端业务/数据模块和外部服务集成，说明依赖及数据权威来源。无需在产品文档中预先设计所有技术细节；当接口、数据或权限影响可实现性时，明确最低必要契约。

## 单项功能规格

| 项目 | 应回答的问题 |
| --- | --- |
| 标识与用户目标 | 为什么需要这项功能？与哪个目标、路径相关？ |
| 角色、入口与前置条件 | 谁能在什么状态下进入或操作？ |
| 输入与校验 | 字段、来源、必填、格式、范围、默认值、校验时机是什么？ |
| 规则、权限与数据 | 谁触发、谁决定结果、数据按什么对象/账户归属？ |
| 状态变化 | 操作前后状态是什么？是否有中间态、超时或外部结果？ |
| 输出与反馈 | 展示什么结果？影响哪些相关页面、记录或通知？ |
| 跳转与退出 | 下一页、返回、取消、撤回、重试会发生什么？草稿是否保留？ |
| 异常与恢复 | 权限不足、无数据、失败或重复操作时，如何解释和恢复？ |
| 验收 | 什么可观察结果代表符合需求？ |

复杂流程补充“角色 × 对象 × 操作 × 状态”的权限矩阵，以及“当前状态—事件—条件—新状态—副作用”的状态表。独立业务过程分别建模，不因界面关联而合并状态；只有定义清楚的事件才能联动。

## 边界与非功能要求

按实际风险检查：加载/空/成功/失败、重复提交、返回与刷新、缺失或极端数据、权限变更、并发/过期、外部结果未知，以及适用的取消/补偿规则。状态按其对象和作用域保存，避免跨对象串状态。

按需要明确性能、可访问性、兼容性、本地化、隐私和安全等可验证要求。不要编造服务承诺、法律结论或实际不存在的集成。
