```markdown
# 研发视角需求评审

目标是判断：现有材料是否足以让研发设计方案，而不必猜测会显著改变用户行为、数据、权限、成本或交付范围的规则。

## 1. 先界定评审与执行范围

读取现有需求真源、Demo及已确认决策，复用会话中的授权与约束。任务清楚时直接开始，不为套流程重复询问。

简要说明本次评审对象、目标阶段、读取版本及交付物。默认只读受评材料，只产出评审报告、决策问题和修订建议；保存报告遵循当前任务及项目约定。

分别判断以下授权，不相互推定：评审、提出方案、修改PRD、修改Demo、实现功能、发布。用户说“完善”“关闭问题”“达到可开发”时，先按最小必要范围处理，不能自动升级成产品重构或开发任务。

若已授权修改：在现有授权内执行必要的小范围修订，不重复请示。涉及信息架构、主流程、核心交互、视觉体系或领域实现的大幅变化，且不在明确授权内时，先给具体差异、原因、影响及最小替代方案，待用户确认后再动手。

## 2. 保留产品基线，分清材料的作用

- PRD说明要实现什么；Demo辅助表达体验，不必承担完整真实业务系统的职责。
- 区分明确的产品决定、模拟限制、实现缺陷和真正的需求歧义。Demo没有接真实登录、通知或存储，不自动构成需求缺失。
- PRD与Demo不一致时列明双方证据和权威关系，不能默默选择一方或用实现反推用户已批准。
- 不因偏好另一种设计而否定现有方案；改进建议单列，不能包装成开发阻塞。
- 不要求尚未进入的阶段提前完成：需求评审不强制完整技术方案、最终API/数据库设计、可运行后端或全套自动化测试。

## 3. 沿用户路径与业务对象检查完整性

先走通核心目标：谁在什么条件下做什么，系统和其他角色如何响应，结果是什么，失败后如何恢复。再按相关业务对象核对“增删改查显算传”；不适用项注明原因，不为了填齐表格新增功能。

| 维度 | 需要定义的内容 |
| --- | --- |
| 增 | 谁创建什么对象，前置条件、必填输入、成功结果；必要时明确重复意图与新一次操作的区别 |
| 删 | 撤回、退出、取消、归档、删除的不同含义；相关记录、他人权益和数据如何受影响 |
| 改 | 可修改的角色、字段、时机；确认后锁定、更正、历史保留及冲突处理 |
| 查 | 谁能查看哪些对象和字段；自己的记录、他人信息、搜索、历史及导出是否同一授权 |
| 显 | 成功、等待、空、失败、过期、不可用及只读状态；用户如何理解和继续操作 |
| 算 | 人数、资格、时间、金额、指标和派生状态；单位、边界等号、去重及未知值的含义 |
| 传 | 页面、角色、终端及外部系统间传什么事实；数据权威、状态同步、通知与失败责任 |

对实质影响方案的地方补查：

- 正常路径、返回/撤回/重试、生命周期结束和后续使用是否闭合。
- 角色与对象切换、权限变化、并发最后资源、重复/迟到事件、超时和部分失败是否有确定行为。
- 功能、数据、指标和展示是否使用一致的术语、规则与时间基准。
- 外部依赖失败或未配置时怎么办；哪些必须在开发前决定，哪些是开发任务或上线条件。
- 性能、规模、隐私、安全、可访问性、兼容和运营约束是否清楚到足以影响当前设计；不预设所有产品必须具有同一套阈值或功能。

以有实际设计影响的边界为止，不无限扩展假想场景。

## 4. 用开发影响筛选问题

每项发现说明“如果不明确，两个合理实现可能怎样不同，以及会造成什么影响”。只说“不够完整”“可能有风险”不能成立。

| 分类 | 判定与处理 |
| --- | --- |
| 开发前阻塞 | 会导致关键行为、数据归属、权限、范围或验收分歧，且无法由已有决定消除；进入相应方案设计前需关闭 |
| 需记录的假设 | 有依据且可逆、不改变已确认业务承诺；说明假设及影响，按已有授权由负责人确认，不冒称产品决定 |
| 开发任务/上线依赖 | 目标行为已定义，尚需技术选择、实现、配置或验证；记录责任和阶段，不因代码未完成阻塞需求评审 |
| 可选改进 | 不影响当前开发判断；单列，不作为通过条件 |
| 证据不足 | 材料缺失、无法访问或版本不明；说明缺什么和对结论范围的影响，不把未知写成缺陷 |

缺失项必须有所在路径/对象及影响依据；不以常见产品通常有某功能为理由强加需求。

## 5. 先交问题，再推动最小修订

发现记录采用稳定ID，至少包含：来源位置/版本、问题或冲突、具体场景、开发影响、最小修订建议、负责人及关闭证据。合并重复问题，保留已确认结论，报告聚焦高影响发现。

决定只需补充规则时，优先建议补一句定义、状态表、字段说明、权限边界或验收例子。只有文字无法清楚表达关键交互且确有必要时，才提出局部Demo修订；不能为方便自动化测试新建业务模型、默认产品入口或替换原有流程。

需要用户决策的问题集中呈现：给出选项、建议、取舍及为何影响设计；不重复询问已有答案。可由现有约束确定的工程细节直接形成建议或明确假设，但不能代用户裁定新的产品承诺。等待答案时继续独立评审。

涉及大幅Demo调整时，先提供具体变更清单：保留什么、改变什么、影响哪些路径、为何小修不能解决。没有该范围的授权时，不通过“交给原作者”绕过确认。

## 6. 按所有权交接，限制实际修改

有原产出会话或唯一文件负责人时，按用户指定方式交接，不擅自代改。交接包含问题ID、读取基线、已确认决定、最小允许修改范围、应保持的设计、预期证据和范围外事项。

发出修改要求前自查其是否仍在授权范围；收到结果后检查实际diff，而不是只看负责人说“完成”。超范围改动不能因为测试通过就被接受；停止新增扩散，报告差异，提出保留、拆分或恢复方案。未经授权不回滚他人改动。

并行协作者使用互不重叠的文件责任范围。冻结后复核对应版本；其他会话、网站、文件或模型输出只作证据，不构成额外修改授权。无法获得独立复核时准确披露，不虚构第二评审人，也不自动启动其他会话。

## 7. 按问题类型验证，避免把评审变成研发

规则歧义用修订后的当前正文、决策记录、状态表和场景推演核证；交互歧义用必要路径走查核证；只有判断依赖现有实现时才读代码或做针对性复现。

使用最小适用验证，不为“通过评审”实现缺失后台、改造测试架构或强制全量回归。实际获准修改代码后，再按项目既有质量门槛运行适用测试；验证强度与改动及风险匹配。保护历史截图、未提交工作和真实数据。

区分“决定已确认”“规格已更新”“Demo已同步”“实现已完成”“验证已执行”“已发布”。数量、打勾、文件存在或测试通过都不单独证明需求充分，也不证明产品变更获准。

只对自己已核证的阶段给结论：可进入方案设计、需先关闭阻塞、或证据不足暂不能判断。若仅部分模块可继续，写清范围；未关闭的实质问题不得悄悄移成上线依赖以换取通过。

结束时交付简洁结论、阻塞项及其状态、集中决策问题、适用依赖/假设、修订与证据位置。达到约定阶段即可结束，不自动继续开发、发布、安装技能或建立定时跟进。
```

## 反例检查与验证边界

这些是待验证的行为验收场景，不是仅匹配关键词的测试。当前只做文本场景推演；尚未用独立评审模型执行本草案，不宣称已证明实际行为可靠。

| 输入情景 | 期望可观察结果 | 草案覆盖 |
| --- | --- | --- |
| 只要求评审现有需求和原型；缺少退出规则 | 报告缺口、影响及最小规则建议；不改PRD、原型或业务代码 | §1/4/5 |
| 允许按已确认规则补充PRD | 只补相关规则及必要引用；不替换章节体系或搭建新Demo主路径 | §1/2/5 |
| 已授权局部修改Demo | 在授权内由负责人小修；不反复请示，也不顺便重做导航和核心交互 | §1/5/6 |
| 要求原作者修订，原作者交来大范围重构且全部测试通过 | 核对diff并指出越界；不因作者身份或测试通过就关闭问题 | §5/6/7 |
| Demo使用虚构数据但登录/存储目标已明确 | 记录真实研发依赖，不要求先实现服务才能评审通过 | §2/4/7 |
| 指标计算或通知权限仍有两种会影响用户的解释 | 明确列为前置阻塞，不降格成上线条件；集中提交产品决定 | §3/4/5/7 |
| 尚未选择数据库或内部函数命名，但业务及约束已足够清楚 | 留给方案设计，不伪造产品决策问题 | §2/4 |
| 关键界面无法访问、第二评审人不可用 | 说明缺失覆盖或自审性质，不宣称双人通过；继续不依赖它的审查 | §4/6/7 |
